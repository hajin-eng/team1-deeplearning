2. 문제 정의

  • 누가 곤란한가: 품질 담당자는 금형을 열어 검사한 뒤에야 불량을 안다. 그때는 재료·시간·설비 가동이 이미 들어간 뒤라, 불량을 안 뒤에는 되돌릴 수 있는 것이 없다.
  • 이 모델이 바꾸는 것: 샷마다 남는 공정·센서 기록(7,535샷 × 32열)만으로 불량 유형을 미리 예측한다. 선별은 불량 가능성이 높은 샷을 먼저 걸러 검사 부담을 줄이는 것, 예방은 불량을 늘리는 공정 조건을 찾아 미리 조정하는 것이다.
  • 맞힐 라벨 7종: 정상 / Short_Shot(미충전) / Blow_Hole(기공) / Exfoliation(박리) / Stain(얼룩) / Deformation(변형) / 기타불량. 정상이 77.6%(4,092샷)라서 모두 "정상"이라 찍어도 정확도는 0.78이다(macro F1은 0.1248). 그래서 지표는 정확도가 아닌 macro F1이다.
  • 두 가지 안: 1안(최종 제출안)은 리더보드 점수를 높이는 모델이다. 2안(현장성을 높인 또 다른 안)은 입력 25개만 써서 실시간 판정이 되고 불량을 더 적극적으로 부르는 현장 후보 모델이다. 두 안의 역할이 달라서 같은 검증으로 나란히 비교했다.

확인 계획확인한 결과처리와 근거

⑥ 처리 기록문제 → 처리 방법 → 판단 근거 → 영향받은 열·행 수를 표로 남겼다.데이터 메모와 보고서 1절. "버린 열 몇 개, 기준은?" 같은 구술 질문에 바로 답할 수 있다
⑦ 금지 사항shot_id·id·Shot은 특징으로 쓰지 않는다. 정답에서 만든 값과 앞뒤 샷의 정답도 쓰지 않는다.앞뒤 샷의 입력은 특징으로 쓴다(1안의 앞뒤 사건 입력 40개)

  • 원인 분석(Q3): 불량 종류마다 "그 종류인가 아닌가"로 RF를 따로 학습하고, 처음 보는 입력에서 순열 중요도로 중요한 조건을 뽑아 구간별 불량률을 직접 센다(Wilson 95% 신뢰구간). 중요도는 원인이 아니므로 같은 제품·같은 시기에서 시험 생산(A/B)으로 확인하기 전까지 "관리 후보"로만 쓴다.

희귀 클래스를 못 맞힌다클래스별로 따로 보고, 끝내 안 되면 한계로 숫자와 함께 보고한다새 입력에서 기타불량 76건 중 0건. 서로 다른 유형을 한 칸에 묶은 라벨이라 어려움을 명시했다
무작위 점수가 시간순보다 높게 나온다시간순 점수를 배포 성능으로 보고하고 차이의 원인을 설명한다1안 0.560 대 0.125. 같은 입력을 외우는 효과와 라벨 분포 변화가 원인이라 설명하고, 운영안은 경보 기준으로 보완했다
public 점수에 맞춰 과적합한다검증 수치를 함께 보고하고 public 점수의 흔들림을 밝힌다public 기준으로 1안을 정했지만 차이 0.028이 표본 흔들림(SD 0.037) 안임을 밝히고 새 입력 약점을 한계로 적었다
