첫 제출에도 데이터 작업은 필요하다. 모델은 정리된 숫자 표만 받을 수 있다. 다만 **모델이 돌아가는 데 필요한 최소한만** 하고, 이상값·중복 판단은 데이터 담당자 분석 후에 정한다.

| 단계 | 담당 |
|---|---|
| 0. 문제 정의 | 공통 |
| 1. 코드 뼈대 | 공통 (모델 파트 주도) |
| 2. 데이터 불러오기 | 데이터 파트 |
| 3. 전처리 | 데이터 파트 (오늘은 모델 파트가 임시로 최소한만) |
| 4. 검증 방식 설계 | 모델 파트 (데이터 파트와 협의) |
| 5. 모델 학습 | 모델 파트 |
| 6. 평가 | 모델 파트 (결과는 Q2·Q3 파트도 사용) |
| 7. 제출 + 재현 확인 | 모델 파트 |

> **"모델에 넣을 수 있는 깨끗한 표"를 만드는 데까지가 데이터 파트, 그 표를 받아 학습·평가·예측하는 것부터가 모델 파트.**

## 단계 1. 코드 뼈대

### 개념: 왜 뼈대부터 만드나
바로 데이터를 읽고 모델을 돌리는 코드를 위에서 아래로 쭉 써도 돌아는 간다. 하지만 이 과제에는 세 가지 요구가 있다.
1. **재현성:** 강사 노트북에서 같은 점수가 나와야 한다.
2. **현장 수정:** 발표 당일 5분 안에 "이 열 빼고 다시 돌려 보세요"에 대응해야 한다.
3. **팀 협업:** 데이터 담당자의 전처리를 나중에 갈아 끼워야 한다.

셋 다 **코드 구조**로 해결하는 문제다. 다 짠 뒤에 구조를 바꾸면 어렵기 때문에 처음에 틀을 잡는다. 현업에서도 "빈 함수로 전체 흐름을 먼저 세우고 하나씩 채우는" 방식을 많이 쓴다.

### 구조 설계: 4개 영역
| 영역 | 내용 | 이유 |
|---|---|---|
| 0. 라이브러리 | import 모음 | 허용 라이브러리만 쓰는지 한눈에 확인 |
| 1. 설정 | 시드, 팀명, 경로, 금지 열 | 바꿀 값이 한곳에 모여 있으면 현장 수정이 빠르다 |
| 2. 단계별 함수 | 단계마다 함수 하나 | 한 단계를 바꿔도 다른 단계가 영향을 받지 않는다 |
| 3. 실행 순서 | `main()` | 전체 흐름을 한 화면에서 읽을 수 있다 |

### 선택지: 다른 방법은?
| 방법 | 장점 | 단점 | 판단 |
|---|---|---|---|
| 함수 없이 위에서 아래로 쭉 | 처음엔 빠름 | 길어지면 어디를 고칠지 찾기 어려움 | ✗ |
| 주피터 노트북 | 탐색에 편함 | 셀 실행 순서에 따라 결과가 달라짐. 노트북만 내면 실격 | 탐색용으로만 |
| 여러 파일로 분리 (`data.py`, `model.py` …) | 큰 프로젝트에 좋음 | 지금 규모에는 과함. 팀장이 파일을 오가며 읽어야 함 | 나중에 커지면 고려 |
| **파일 하나 + 함수 분리** | 명령 한 줄 규칙과 맞고 읽기 쉬움 | 파일이 길어질 수 있음 | ✓ 이번 선택 |

### 코드 설명

**맨 위 설명문(docstring)**
파일을 연 사람이 가장 먼저 보는 곳이다. 무엇을 하는 코드이고 어떻게 실행하는지 적어 둔다. 강사가 채점할 때도 이 부분을 먼저 본다.

**0. 라이브러리**
- `random`, `time`, `pathlib`는 파이썬 기본 라이브러리라 규칙에 걸리지 않는다.
- 기본 라이브러리 → 외부 라이브러리 순서로 한 줄 띄워 쓰는 것이 파이썬 관례(PEP 8)다.
- scikit-learn은 5단계에서 실제로 쓸 때 추가한다.

**1. 설정**
- **대문자 변수명**(`SEED`, `TEAM_NAME`)은 "프로그램 실행 중 바뀌지 않는 설정값"이라는 파이썬 관례다.
- `SEED = 42`: 숫자 자체에는 의미가 없다. 어떤 숫자든 **고정**하는 것이 중요하다. 42는 관례로 많이 쓰는 값이다.
- **경로를 `Path(__file__).resolve().parent` 기준으로 만든 이유**
  - `__file__`은 "지금 실행 중인 파이썬 파일(main.py)의 위치"다. `.resolve().parent`는 그 파일이 들어 있는 폴더다.
  - 그냥 `"data/주조공정_입력.csv"`라고 쓰면, 다른 폴더에서 `python 학생배포/main.py`로 실행할 때 파일을 못 찾는다. 상대경로가 "지금 터미널이 있는 위치" 기준이기 때문이다.
  - `__file__` 기준으로 만들면 어디서 실행해도 main.py 옆의 파일을 찾는다.
  - 규칙이 금지하는 것은 `C:\Users\...`처럼 **내 컴퓨터에만 있는 경로를 직접 적는 것**이다. `__file__` 방식은 실행할 때 위치를 계산하므로 강사 노트북에서도 그대로 작동한다.
  - `/` 연산자로 경로를 이어 붙이면 윈도우(`\`)와 맥(`/`)의 차이를 pathlib가 알아서 처리한다.
- `ID_COLS`: 금지 열을 이름으로 박아 두고 3단계에서 이 목록으로 제외한다. 실수로 들어가는 것을 막는 장치다.

**2. 단계별 함수**
- 함수 이름이 곧 단계 이름이다. 함수 이름만 읽어도 전체 흐름이 보인다.
- `raise NotImplementedError`: "아직 안 만들었다"는 표시다. 실수로 호출하면 조용히 넘어가지 않고 바로 오류를 낸다. `pass`를 쓰면 아무 일도 안 하고 넘어가서 버그를 늦게 발견한다.
- **`set_seed()`에서 시드를 고정하는 이유:** 컴퓨터의 "무작위"는 사실 시드라는 출발 숫자로 계산된 정해진 수열이다. 시드가 같으면 같은 무작위 값이 나온다. 이 프로젝트에서 무작위가 쓰이는 곳은 검증 분할, 랜덤포레스트의 나무 만들기, MLP의 초기 가중치다. 고정하지 않으면 실행할 때마다 점수가 달라진다.
- **torch를 `try / except ImportError`로 감싼 이유:** 지금 컴퓨터에 PyTorch가 없다. 그냥 `import torch`를 쓰면 프로그램이 멈춘다. 이렇게 감싸면 torch가 있으면 시드를 고정하고, 없으면 건너뛴다. MLP 단계에서 torch를 설치하면 자동으로 적용된다.
- scikit-learn 모델은 `random_state=SEED`를 모델마다 따로 넣어 준다 (4·5단계에서).

**3. 실행 순서**

## 단계 2. 데이터 불러오기

### 개념: 이 단계에서 하는 일
흩어져 있는 파일 3개를 **샷 하나 = 행 하나**인 표 하나로 합친다.

| 파일 | 가진 정보 | 행 수 |
|---|---|---|
| `data/주조공정_입력.csv` | 공정 조건 + 센서값 | 7,535 |
| `분할표.csv` | 그 샷이 train / public / private 중 어디인지 | 7,535 |
| `정답_train.csv` | 정답 라벨 | 5,274 (train만) |

세 파일을 이어 주는 공통 열(**키**)은 `shot_id`다.

이 단계의 핵심은 **"읽기"보다 "검증"**이다. 데이터를 잘못 합쳐도 파이썬은 오류를 내지 않는다. 행이 조용히 사라지거나 늘어나고, 모델은 그 잘못된 데이터로 그대로 학습한다. 점수가 이상하게 나온 뒤에야 원인을 찾게 된다. 그래서 **합친 직후에 "있어야 할 모습"을 코드로 검사한다.**

### 이 데이터에서 주의할 점 3가지
1. **헤더가 2줄이다.** 1행은 `Process / Sensor` 그룹 이름, 2행이 실제 컬럼명이다. 그냥 읽으면 그룹 이름이 컬럼명이 되고, 실제 컬럼명은 데이터 첫 행으로 들어간다.
2. **컬럼명에 공백이 있다.** `'Biscuit_Thickness '`, `'Clamping_Force '`, `' Pressure_Rise_Time'`. 공백을 그대로 두면 `df["Clamping_Force"]`로 꺼낼 때 오류가 난다. 눈으로는 공백이 안 보여서 원인을 찾기 어렵다.
3. **정답 파일은 train에만 있다.** 합치는 방법을 잘못 고르면 제출 대상 2,261행이 사라진다 (아래 merge 설명).

### 선택지

**헤더 2줄 처리**
| 방법 | 설명 | 판단 |
|---|---|---|
| `header=1` | 2번째 줄(0부터 세서 1)을 컬럼명으로 쓰고 1번째 줄은 버림 | ✓ 이번 선택 |
| `skiprows=1` | 첫 줄을 건너뛰고 읽음. 결과는 같음 | 같은 효과 |
| `header=[0, 1]` | 두 줄 모두 컬럼명으로 씀 (2층 컬럼) | ✗ Process/Sensor 구분이 남지만 컬럼 다루기가 번거로움. 그룹 정보는 컬럼 목록을 보면 알 수 있음 |

**파일 합치기 (`merge`의 `how`)**
| 방법 | 결과 | 판단 |
|---|---|---|
| `how="inner"` (기본값) | 양쪽에 다 있는 shot_id만 남김 → 정답이 없는 제출 대상 2,261행이 **사라짐** (5,274행만 남음) | ✗ 위험 |
| `how="left"` | 왼쪽(입력 파일)의 행을 전부 유지. 정답이 없으면 빈칸(NaN) | ✓ 이번 선택 |

> ⚠️ `merge`의 기본값이 `inner`라서 아무 생각 없이 쓰면 제출 대상이 사라진다. 실제로 확인해 보니 inner로 합치면 5,274행만 남았다.

**검증 방법**
| 방법 | 설명 | 판단 |
|---|---|---|
| `print`로 찍어서 눈으로 확인 | 간단하지만 매번 사람이 봐야 하고 놓치기 쉬움 | 보조로만 |
| `assert` | 조건이 틀리면 즉시 멈추고 이유를 출력 | ✓ 이번 선택 |
| `if ...: raise ValueError(...)` | assert와 같지만 더 엄격한 방식 (파이썬 최적화 모드에서도 꺼지지 않음) | 큰 시스템에서 사용 |

### 코드

**① 설정 영역에 추가** (`TARGET_COL = "label"` 아래)
```python
LABELS = ["정상", "불량_Short_Shot", "불량_Blow_Hole", "불량_Exfoliation",
          "불량_Stain", "불량_Deformation", "기타불량"]   # 제출 가능한 라벨 7종

N_TOTAL, N_TRAIN, N_TEST = 7535, 5274, 2261           # 있어야 할 행 수
```

**② `load_data()` 함수 교체**
```python
def load_data():
    """[2단계] 입력·분할표·정답을 읽어 하나의 표로 합친다."""
    # (1) 파일 읽기
    inputs = pd.read_csv(INPUT_PATH, header=1, encoding="utf-8-sig")
    inputs.columns = inputs.columns.str.strip()          # 컬럼명 앞뒤 공백 제거
    split = pd.read_csv(SPLIT_PATH, encoding="utf-8-sig")
    labels = pd.read_csv(LABEL_PATH, encoding="utf-8-sig")

    # (2) shot_id 기준으로 합치기
    df = inputs.merge(split, on="shot_id", how="left", validate="one_to_one")
    df = df.merge(labels, on="shot_id", how="left", validate="one_to_one")
    df = df.sort_values("shot_id").reset_index(drop=True)

    # (3) 검증: 있어야 할 모습과 다르면 즉시 멈춘다
    is_train = df["split"] == "train"
    assert len(df) == N_TOTAL, f"전체 행 수가 {len(df)}개"
    assert df["split"].notna().all(), "분할 정보가 없는 샷이 있음"
    assert is_train.sum() == N_TRAIN, f"train 행 수가 {is_train.sum()}개"
    assert (~is_train).sum() == N_TEST, f"제출 대상 행 수가 {(~is_train).sum()}개"
    assert df.loc[is_train, TARGET_COL].notna().all(), "정답이 없는 train 샷이 있음"
    assert df.loc[~is_train, TARGET_COL].isna().all(), "제출 대상에 정답이 붙어 있음"
    assert df.loc[is_train, TARGET_COL].isin(LABELS).all(), "알 수 없는 라벨이 있음"

    print(f"[2단계] 데이터 불러오기 완료: 전체 {len(df)}행 × {df.shape[1]}열 "
          f"(train {is_train.sum()} / 제출 대상 {(~is_train).sum()})")
    return df
```

**③ `main()`에서 2단계 주석 풀기**
```python
    df = load_data()                      # 2단계
```

### 코드 설명

**설정 추가**
- `LABELS`: 정답으로 나올 수 있는 7종 문자열. 지금은 정답 검사에 쓰고, 7단계에서 제출 파일 검사에도 다시 쓴다. 한곳에 적어 두면 오타가 나도 한곳만 고치면 된다.
- `N_TOTAL, N_TRAIN, N_TEST`: 설명서에 적힌 숫자다. 코드 안에 `7535`를 직접 쓰는 대신 이름을 붙이면 "이 숫자가 무엇인지" 읽는 사람이 바로 안다. 이름 없이 코드에 박힌 숫자를 **매직 넘버**라고 하며, 피하는 것이 좋다.

**(1) 파일 읽기**
- `header=1`: 2번째 줄을 컬럼명으로 쓴다.
- `encoding="utf-8-sig"`: 이 CSV 파일들은 맨 앞에 **BOM**이라는 보이지 않는 표시 문자가 붙어 있다 (엑셀에서 한글이 깨지지 않게 하려고 붙이는 표시). `utf-8-sig`는 "BOM이 있으면 떼고 읽어라"라는 뜻이다. 지금 pandas는 BOM을 알아서 처리하지만, 버전이나 환경에 따라 첫 컬럼명이 `'\ufeffshot_id'`처럼 읽히는 경우가 있다. 그러면 `shot_id`로 합치기가 실패한다. 강사 노트북 환경을 모르기 때문에 명시해 두는 것이 안전하다.
- `inputs.columns.str.strip()`: 모든 컬럼명의 앞뒤 공백을 지운다. `str.strip()`은 문자열 양끝의 공백을 지우는 함수이고, `.str`을 붙이면 컬럼명 전체에 한 번에 적용된다.

**(2) 합치기**
- `merge(..., on="shot_id")`: 두 표에서 shot_id가 같은 행끼리 옆으로 붙인다. 엑셀의 VLOOKUP과 같은 작업이다.
- `how="left"`: 입력 파일 7,535행을 전부 유지한다. 정답이 없는 제출 대상 행에는 `label` 칸이 빈칸(NaN)으로 들어간다.
- `validate="one_to_one"`: "양쪽 모두 shot_id가 하나씩만 있어야 한다"는 조건이다. 한쪽에 같은 shot_id가 두 번 있으면 합칠 때 행이 복제되어 늘어난다. 이 옵션을 넣으면 그런 경우 즉시 오류를 낸다.
- `sort_values("shot_id")`: 생산 순서대로 정렬한다. 나중에 시간순 분할(보고서 6번)을 할 때 이 순서가 필요하다.
- `reset_index(drop=True)`: 정렬하면 행 번호가 뒤섞이므로 0부터 다시 매긴다. `drop=True`는 옛 행 번호를 열로 남기지 말라는 뜻이다.

**(3) 검증**
- `assert 조건, "메시지"`: 조건이 거짓이면 프로그램을 멈추고 메시지를 보여 준다.
- `is_train`: 각 행이 train인지 True/False로 담은 열. `~is_train`은 반대(제출 대상)다. `~`는 True와 False를 뒤집는 기호다.
- 검사 7개는 각각 "합치기에서 생길 수 있는 사고"에 하나씩 대응한다.

| 검사 | 막는 사고 |
|---|---|
| 전체 7,535행 | 합치다가 행이 사라지거나 늘어남 |
| 분할 정보 빈칸 없음 | 분할표에 없는 샷이 섞임 |
| train 5,274 / 제출 대상 2,261 | 분할 정보가 잘못 붙음 |
| train에 정답 빈칸 없음 | 정답 파일과 shot_id가 안 맞음 |
| 제출 대상에 정답 없음 | 엉뚱한 정답이 붙음 (정보 유출) |
| 라벨이 7종 안에 있음 | 오타나 다른 형식의 라벨 |

- `df.loc[행 조건, 열 이름]`: 조건에 맞는 행의 특정 열만 꺼낸다. 예: `df.loc[is_train, "label"]` = train 행의 label 열

**print 메시지**
단계마다 `[2단계]`처럼 단계 번호를 붙여 출력한다. 전체를 돌렸을 때 어느 단계까지 진행됐고 어디서 멈췄는지 바로 보인다.

```

```

## 단계 3. 최소 전처리

### 개념: 이 단계에서 하는 일
2단계에서 만든 표(34열)에서 **모델에 넣을 열(피처)만 남긴 표**를 만든다.

### 핵심 원칙: 전처리는 두 종류로 나뉜다
| 종류 | 뜻 | 예시 | 어디서 하나 |
|---|---|---|---|
| **규칙형 처리** | 데이터 값을 보고 계산하지 않고, 사람이 정한 규칙대로 하는 처리 | 금지 열 빼기, 상수열 빼기, 컬럼명 정리 | **3단계 `preprocess()`** |
| **학습형 처리** | 데이터에서 값을 계산해서 쓰는 처리 | 결측을 중앙값으로 채우기, 표준화(평균·표준편차로 크기 맞추기) | **5단계 Pipeline 안** |

**학습형 처리를 따로 두는 이유: 정보 유출(data leakage) 방지**
- 결측을 "train 전체의 중앙값"으로 채운다고 하자. 그런데 4단계에서 train을 학습용 / 검증용으로 나눈다. 전체 중앙값을 쓰면 **검증용 데이터의 값이 섞인 중앙값**으로 학습용 데이터를 채우게 된다.
- 검증용은 "모델이 처음 보는 데이터" 역할인데, 그 정보가 학습에 미리 새어 들어간 셈이다. 검증 점수가 실제보다 좋게 나온다.
- 현장으로 바꿔 말하면, 오늘 모델을 만들 때 "내일 생산될 샷의 값"을 미리 쓴 것과 같다.
- 그래서 **값을 계산하는 처리는 반드시 학습용 데이터로만 계산**해야 한다. scikit-learn의 **Pipeline**이 이것을 자동으로 지켜 준다 (5단계).
- 이 데이터에서는 결측이 90행뿐이라 영향이 작다. 하지만 표준화나 다른 처리가 추가되면 영향이 커지므로 처음부터 원칙대로 만든다.

### 오늘 할 처리와 하지 않을 처리
| 처리 | 대상 | 오늘 | 이유 |
|---|---|---|---|
| 식별 열 제외 | `shot_id`, `id`, `Shot` | ✓ 제외 | 피처로 쓰면 실격 |
| 피처가 아닌 열 제외 | `split`, `label` | ✓ 제외 | `split`은 분할 정보, `label`은 정답 |
| 상수열 제외 | `*_Min`, `*_Max` 8개 | ✓ 제외 | 값이 하나뿐이라 정상과 불량을 구분하지 못함 |
| 결측 채우기 | `Factory_Temp`, `Factory_Humidity` (각 90행) | 5단계에서 | 학습형 처리라서 Pipeline 안에서 함 |
| 이상값 처리 | High_Velocity=0, Cycle_Time>60 등 | ✗ 그대로 둠 | 데이터 파트가 판단할 일 |
| 이중기록 처리 | 2,918쌍 | ✗ 그대로 둠 | 4단계 검증 방식에서 다룸 |
| Product_Type | 값 1, 2 | 그대로 사용 | 아래 설명 |

**결측 행을 지우면 안 되는 이유:** 결측 90행 중 **27행이 제출 대상**이다. 제출 대상 행은 하나라도 빠지면 실격이므로 지울 수 없다. 반드시 채워야 한다.

**Product_Type을 그대로 쓰는 이유:** 범주형 값(종류를 나타내는 값)은 보통 원-핫 인코딩(종류마다 0/1 열을 하나씩 만드는 방법)으로 바꾼다. 숫자 크기에 의미가 없기 때문이다. 하지만 종류가 2개뿐이면 "1이냐 2냐" 하나의 열로 충분히 구분된다. 원-핫으로 바꿔도 정보가 같다. 종류가 3개 이상이면 원-핫이 필요하다.

### 선택지

**결측 채우기 방법 (5단계에서 적용)**
| 방법 | 설명 | 판단 |
|---|---|---|
| 결측 행 삭제 | 제출 대상 27행도 지워야 함 | ✗ 실격 |
| 열 삭제 | 공장 온도·습도 정보를 통째로 잃음 | ✗ 정보 손실이 큼 |
| 평균으로 채우기 | 이상값이 있으면 평균이 끌려감 | △ |
| **중앙값으로 채우기** | 이상값에 덜 흔들림. 가장 흔한 기본 선택 | ✓ 첫 제출용 |
| 앞 샷의 값으로 채우기 | 센서값은 시간에 따라 천천히 변하므로 그럴듯함. 결측이 154샷 구간에 몰려 있어서 긴 구간을 한 값으로 채우게 됨 | 데이터 파트 검토 후보 |
| 결측 여부 표시 열 추가 | "이 샷은 온도 기록이 없었다"를 모델이 알게 함 | 데이터 파트 검토 후보 |

> 앞 샷의 **입력값**을 쓰는 것은 규칙 위반이 아니다. 금지된 것은 앞 샷의 **정답**을 쓰는 것이다.

**상수열을 고르는 방법**
| 방법 | 설명 | 판단 |
|---|---|---|
| 자동 탐지 (`nunique() == 1`인 열을 찾아서 빼기) | 편리함. 하지만 데이터가 바뀌면 빠지는 열이 조용히 바뀜 | △ |
| **목록으로 직접 적기 + 정말 상수인지 assert로 확인** | 무엇을 뺐는지 코드에 명확히 남음. 보고서·구술 질문 "버린 열이 몇 개고 무슨 기준입니까?"에 바로 답할 수 있음 | ✓ 이번 선택 |

### 코드

**① 설정 영역에 추가** (`ID_COLS` 아래)
```python
CONSTANT_COLS = ["Air_Pressure_Min", "Air_Pressure_Max",          # 모든 행에서 값이 하나뿐인 열
                 "Coolant_Temp_Min", "Coolant_Temp_Max",          # (관리 기준 범위로 보임)
                 "Factory_Temp_Min", "Factory_Temp_Max",
                 "Factory_Humidity_Min", "Factory_Humidity_Max"]
EXTRA_DROP_COLS = []    # 추가로 뺄 열 (현장 수정: "이 열 빼고 돌려 보세요" → 여기에 이름 추가)
```

**② `preprocess()` 함수 교체**
```python
def preprocess(df):
    """[3단계] 모델에 넣을 피처 표를 만든다. (데이터 파트 결과로 교체될 부분)

    여기서는 규칙형 처리(열 빼기)만 한다.
    결측 채우기처럼 데이터에서 값을 계산하는 처리는 5단계 Pipeline 안에서 한다.
    """
    non_feature_cols = ID_COLS + ["split", TARGET_COL]
    drop_cols = non_feature_cols + CONSTANT_COLS + EXTRA_DROP_COLS

    # 상수열이 정말 상수인지 확인 (결측은 빼고 센다)
    for col in CONSTANT_COLS:
        assert df[col].nunique() == 1, f"{col}은 상수열이 아님"

    X = df.drop(columns=drop_cols)

    # 검증
    assert len(X) == N_TOTAL, "전처리 중에 행 수가 바뀜"
    assert not set(ID_COLS) & set(X.columns), "식별 열이 피처에 들어감"
    assert all(pd.api.types.is_numeric_dtype(X[c]) for c in X.columns), "숫자가 아닌 열이 있음"

    n_missing = X.isna().sum()
    print(f"[3단계] 전처리 완료: 피처 {X.shape[1]}개 (제외 {len(drop_cols)}개) "
          f"/ 결측이 있는 열: {n_missing[n_missing > 0].to_dict()}")
    return X
```

**③ `main()`에서 3단계 주석 풀기**
```python
    X = preprocess(df)                  # 3단계
```

### 코드 설명

**설정 추가**
- `CONSTANT_COLS`: 데이터 확인에서 찾은 상수열 8개를 직접 적었다. 주석에 "왜 빼는지"를 함께 남긴다.
- `EXTRA_DROP_COLS`: 지금은 비어 있다. 발표 당일 "이 열을 빼고 다시 돌려 보세요"라는 요청이 오면 **여기에 열 이름 하나만 추가**하면 된다. 현장 수정 대비용 자리다.

**함수 설명문**
"여기서는 규칙형 처리만 한다"는 원칙을 적어 둔다. 나중에 데이터 담당자가 이 함수를 고칠 때 결측 채우기 같은 처리를 여기에 넣지 않도록 알려 주는 역할이다.

**제외할 열 모으기**
- `non_feature_cols`: 피처가 아닌 열 (식별 열 3개 + `split` + `label`)
- `drop_cols`: 제외할 열 전체 = 피처 아닌 열 5개 + 상수열 8개 + 추가 제외 열
- 리스트는 `+`로 이어 붙일 수 있다.

**상수열 확인**
- `df[col].nunique()`: 그 열에 서로 다른 값이 몇 종류 있는지 센다. 결측(NaN)은 세지 않는다. 그래서 Factory_Temp_Min처럼 결측이 있는 열도 상수열로 판정된다.
- 목록을 직접 적었기 때문에, 데이터가 바뀌어서 상수가 아니게 되면 조용히 지나가지 않고 여기서 멈춘다.

**열 빼기**
- `df.drop(columns=drop_cols)`: 목록에 있는 열을 뺀 **새 표**를 만든다. 원래 `df`는 그대로 남는다. `df`에는 split, label, shot_id가 남아 있어야 4단계와 7단계에서 쓸 수 있다.
- 행은 건드리지 않는다. 그래서 `X`의 행 순서는 `df`와 같다. 나중에 `df`의 split 정보로 `X`의 train 행과 제출 대상 행을 나눈다.

**검증 3개**
| 검사 | 막는 사고 |
|---|---|
| 행 수가 7,535 그대로 | 전처리 중에 행이 사라짐 (제출 대상이 빠지면 실격) |
| 식별 열이 피처에 없음 | 실격 규칙 위반 |
| 모든 피처가 숫자 | 문자가 섞이면 모델이 학습하지 못함 |

- `set(ID_COLS) & set(X.columns)`: 두 목록의 **교집합**(둘 다에 있는 것)이다. 비어 있어야 정상이다. `not`을 붙였으므로 "교집합이 비어 있다"를 검사한다.
- `pd.api.types.is_numeric_dtype()`: 그 열이 숫자형인지 확인하는 pandas 함수

**결측 출력**
`X.isna().sum()`은 열마다 결측 개수를 센다. 그중 0보다 큰 열만 골라 출력한다. 결측은 5단계에서 채우므로 지금은 "얼마나 있는지"만 확인한다.

### 정리
- 전처리는 **규칙형**(사람이 정한 규칙, 3단계)과 **학습형**(데이터에서 값을 계산, 5단계 Pipeline)으로 나눈다.
- 학습형 처리를 학습용 데이터로만 계산하는 이유는 **정보 유출 방지**다.

- 상수열은 목록으로 직접 적고 assert로 확인한다 → 무엇을 왜 뺐는지 코드에 남는다.
- `EXTRA_DROP_COLS`가 현장 수정 대비용 자리다.
- **구술 대비:** "버린 열이 몇 개고 무슨 기준이었습니까?" → "식별 열 3개는 규칙상 제외, 상수열 8개는 모든 샷에서 값이 하나뿐이라 정상과 불량을 구분하는 정보가 없어서 제외했습니다. 총 11개입니다."
- **데이터 파트에 넘길 것:** 결측 채우는 방법(중앙값 vs 앞 샷 값 vs 결측 표시 열), 이상값 처리, 이중기록 처리

## 단계 4. 검증 방식 설계

### 개념: 이 단계에서 하는 일
train 5,274샷을 **학습용**과 **검증용**으로 나눈다. 모델은 학습용으로만 배우고, 검증용으로 채점한다. 검증용은 "모델이 처음 보는 샷" 역할을 한다.

### 왜 모델보다 먼저 정하나
검증 방식은 **채점 기준**이다. 채점 기준이 잘못되면 이런 문제가 생긴다.
- 나쁜 모델이 좋아 보인다.
- 모델끼리 비교할 때 엉뚱한 모델을 고른다.
- 현장에 걸었을 때 성능이 생각보다 훨씬 낮다.

모델을 먼저 만들고 검증 방식을 나중에 정하면, "점수가 잘 나오는 검증 방식"을 무의식적으로 고르게 된다. 그래서 현업에서는 **채점 방법을 먼저 정하고 그다음에 모델을 만든다.**

### 이 데이터의 함정: 쌍둥이 행
- 같은 샷이 두 번 기록된 쌍이 2,918쌍 있다. 두 행은 입력값도 정답도 똑같다.
- 무작위로 나누면 쌍둥이 하나는 학습용에, 다른 하나는 검증용에 들어갈 수 있다. 모델은 학습용에서 본 행을 기억해서 검증용 쌍둥이를 맞힌다. **시험 문제를 미리 보고 시험을 치는 상황**이다.
- 실제로 무작위 80/20으로 나눠 보니 **검증용 1,055행 중 464행(44%)의 쌍둥이가 학습용에 있었다.**

### 미리 해 본 실험: 분할 방법에 따라 점수가 얼마나 달라지나
같은 모델, 같은 피처로 분할 방법만 바꿔서 검증 macro F1을 쟀다.

| 모델 | 무작위 80/20 | **그룹 분할 80/20** | 시간순 80/20 |
|---|---|---|---|
| 로지스틱 (class_weight) | 0.219 | 0.239 | 0.102 |
| 랜덤포레스트 | **0.455** | 0.274 | 0.111 |
| 1-NN (가장 비슷한 행 하나를 베낌) | **0.489** | 0.257 | 0.211 |

**해석**
1. **외우는 모델일수록 무작위 분할에서 점수가 부풀려진다.**
   - 1-NN은 "가장 비슷한 학습 행의 정답을 그대로 베끼는" 모델이다. 쌍둥이가 있으면 무조건 맞힌다. 그래서 무작위 분할에서 0.489로 1등이다.
   - 랜덤포레스트도 0.455에서 0.274로 크게 떨어진다.
   - 로지스틱은 외우지 못하는 단순한 모델이라 거의 차이가 없다.
   - 무작위 분할로 모델을 고르면 "외우기를 잘하는 모델"을 고르게 된다.
2. **시간순 분할에서는 모든 모델이 무너진다 (0.10~0.21).**
   - 불량이 시기별로 몰려 있어서 과거로 배운 패턴이 미래에 잘 맞지 않는다.
   - 이것이 "현장에 배포했을 때의 성능"에 가장 가깝다. 보고서 6번의 핵심 결과가 된다.
3. **리더보드에도 같은 일이 생길 수 있다.** 제출 대상 2,261샷 중 약 1,207샷은 쌍둥이가 train에 있다. 그래서 public 점수는 무작위 분할처럼 부풀려질 가능성이 크다. public 점수만 보고 모델을 고르면 안 되는 이유가 하나 더 생겼다.

### 세 가지 분할이 각각 재는 것
| 분할 | 재는 것 | 용도 |
|---|---|---|
| 무작위 | 이미 본 샷을 다시 맞히는 능력 (외우기 포함) | 비교용. 모델 선택에는 쓰지 않음 |
| **그룹 분할** | **같은 시기에 생산된, 처음 보는 샷을 맞히는 능력** | **모델 선택 기준 (이번 선택)** |
| 시간순 | 미래에 생산될 샷을 맞히는 능력 | 배포 성능 추정 (보고서 6번) |

### 선택지
| 방법 | 설명 | 판단 |
|---|---|---|
| 무작위 분할 (`train_test_split`) | 가장 흔한 방법. 쌍둥이가 갈라짐 | ✗ 점수가 부풀려짐 |
| 중복 행 삭제 후 무작위 분할 | 쌍둥이 중 하나를 지워 문제를 없앰 | △ 데이터를 바꾸는 결정이라 데이터 파트와 합의 필요 |
| **그룹 분할** | 쌍둥이를 한 그룹으로 묶어 같은 쪽에 넣음. 데이터는 그대로 둠 | ✓ 이번 선택 |
| 시간순 분할 | 앞 80% 학습, 뒤 20% 검증 | 보고서 6번에서 따로 잰다 |

**그룹 분할 중에서도 `StratifiedGroupKFold`를 쓰는 이유**
- **Group:** 쌍둥이가 갈라지지 않게 한다.
- **Stratified(층화):** 학습용과 검증용의 클래스 비율을 맞춘다. 기타불량은 76건뿐이라 무작위로 나누면 검증용에 5건만 들어갈 수도 있고 25건이 들어갈 수도 있다. 층화하면 약 20%인 15건 정도가 들어가도록 맞춘다.
- **KFold:** 데이터를 5조각으로 나누는 도구다. 이번에는 그중 **첫 번째 조각 하나만** 검증용으로 쓴다 (80/20 한 번). 나중에 5조각을 모두 돌리는 교차검증으로 확장하기 쉽다.

**한 번만 나누기(홀드아웃) vs 5겹 교차검증**
| 방법 | 장점 | 단점 | 언제 |
|---|---|---|---|
| **홀드아웃 (80/20 한 번)** | 빠르고 단순함. 혼동행렬·임계값 분석이 쉬움 | 소수 클래스가 15~20건뿐이라, 어떻게 나뉘었느냐에 따라 점수가 흔들림 | ✓ 첫 제출 |
| 5겹 교차검증 | 5번 평균이라 점수가 안정적 | 5배 오래 걸림 | 모델 비교 단계 (10/20~) |

### 코드

**① 설정 영역에 추가**
```python
VALID_FOLDS = 5    # train을 5조각으로 나눠 1조각을 검증용으로 쓴다 (= 검증용 20%)
```

**② import 추가** (라이브러리 영역, `import pandas as pd` 아래)
```python
from sklearn.model_selection import StratifiedGroupKFold
```

**③ 쌍둥이 그룹 함수 추가** (`preprocess()` 아래에 새 함수)
```python
def make_twin_groups(df):
    """[4단계] 같은 샷이 두 번 기록된 쌍둥이 행에 같은 그룹 번호를 붙인다.

    쌍둥이 = 바로 앞 행과 입력값(Shot 포함)이 전부 같은 행
    """
    input_cols = [c for c in df.columns if c not in ("shot_id", "id", "split", TARGET_COL)]
    values = df[input_cols].fillna(-1)                    # 결측끼리도 같다고 비교하기 위해
    same_as_prev = values.eq(values.shift()).all(axis=1)  # 바로 앞 행과 모든 열이 같은가
    groups = (~same_as_prev).cumsum()                     # 앞 행과 다를 때마다 그룹 번호 +1

    print(f"[4단계] 쌍둥이 그룹: 바로 앞 행과 같은 행 {same_as_prev.sum()}개 "
          f"→ 그룹 {groups.nunique()}개")
    return groups
```

**④ `split_validation()` 함수 교체** (입력이 `train_df`에서 `df, groups`로 바뀜)
```python
def split_validation(df, groups):
    """[4단계] train 안에서 학습용 / 검증용을 나눈다.

    쌍둥이는 같은 쪽에 넣고(Group), 클래스 비율은 양쪽이 같게 맞춘다(Stratified).
    """
    train_idx = df.index[df["split"] == "train"]
    y = df.loc[train_idx, TARGET_COL]
    g = groups.loc[train_idx]

    sgkf = StratifiedGroupKFold(n_splits=VALID_FOLDS, shuffle=True, random_state=SEED)
    fit_pos, valid_pos = next(sgkf.split(train_idx, y, g))   # 5조각 중 첫 번째만 사용
    fit_idx, valid_idx = train_idx[fit_pos], train_idx[valid_pos]

    # 검증
    assert len(fit_idx) + len(valid_idx) == N_TRAIN, "학습용 + 검증용이 train 수와 다름"
    assert not set(groups.loc[fit_idx]) & set(groups.loc[valid_idx]), "쌍둥이가 양쪽에 나뉘어 들어감"

    print(f"[4단계] 검증 분할: 학습용 {len(fit_idx)} / 검증용 {len(valid_idx)}")
    counts = pd.DataFrame({"학습용": df.loc[fit_idx, TARGET_COL].value_counts(),
                           "검증용": df.loc[valid_idx, TARGET_COL].value_counts()})
    print(counts.reindex(LABELS).to_string())
    return fit_idx, valid_idx
```

**⑤ `main()`에 추가** (3단계 아래)
```python
    groups = make_twin_groups(df)                         # 4단계
    fit_idx, valid_idx = split_validation(df, groups)     # 4단계
```

### 코드 설명

**함수 입력을 바꾼 이유**
1단계 뼈대에서는 `split_validation(train_df)`였다. 그런데 쌍둥이 그룹을 찾으려면 **train만이 아니라 전체 데이터에서 "바로 앞 행"을 봐야 한다.** train만 떼어 내면 사이에 있던 제출 대상 행이 빠지면서, 원래 붙어 있지 않던 행끼리 붙게 된다. 그래서 그룹은 전체 `df`로 만들고 분할 함수에 넘겨준다. 설계는 이렇게 진행하면서 고쳐 나가는 것이 자연스럽다.

**`make_twin_groups()` 한 줄씩**
- `input_cols`: 비교할 열. `shot_id`와 `id`는 행마다 항상 다르므로 뺀다. `split`과 `label`은 입력값이 아니므로 뺀다. **`Shot`은 포함한다.** Shot 번호까지 같아야 같은 샷이기 때문이다.
  - `[c for c in 목록 if 조건]`은 **리스트 컴프리헨션**이다. "목록에서 조건에 맞는 것만 모은 새 목록"을 한 줄로 만드는 문법이다.
- `fillna(-1)`: 결측(NaN)끼리 비교하면 파이썬은 "다르다"고 판단한다 (`NaN == NaN`은 False). 결측 구간에 있는 쌍둥이를 놓치지 않으려고 비교할 때만 임시로 -1로 바꾼다. 원래 데이터는 바뀌지 않는다.
- `values.shift()`: 표 전체를 한 줄 아래로 민다. 그러면 각 행 자리에 "바로 앞 행"이 오게 된다.
- `values.eq(values.shift())`: 칸마다 "앞 행과 같은가"를 True/False로 낸다.
- `.all(axis=1)`: 한 행의 모든 칸이 True인가를 본다. `axis=1`은 "가로 방향(행 단위)으로"라는 뜻이다.
- `(~same_as_prev).cumsum()`: **그룹 번호를 붙이는 요령**이다.

```
행:             A    A'   B    C    C'   D
앞 행과 같은가:  F    T    F    F    T    F
뒤집기(~):      T    F    T    T    F    T     (True = 새 그룹 시작)
누적합:         1    1    2    3    3    4     ← 그룹 번호
```
`cumsum()`은 위에서부터 차례로 더해 가는 **누적합**이다. True는 1, False는 0으로 더해진다. 새 그룹이 시작될 때만 번호가 1씩 올라가므로 쌍둥이는 같은 번호를 받는다.

**`split_validation()` 한 줄씩**
- `train_idx`: train 행의 행 번호 목록
- `StratifiedGroupKFold(n_splits=5, shuffle=True, random_state=SEED)`
  - `n_splits=5`: 5조각으로 나눈다. 1조각이 20%다.
  - `shuffle=True`: 그룹 순서를 섞은 뒤 나눈다. 섞지 않으면 앞쪽 그룹이 한 조각에 몰린다.
  - `random_state=SEED`: 섞는 방법을 고정한다. scikit-learn은 numpy 시드와 별도로 이렇게 직접 넣어 주는 것이 확실하다.
- `sgkf.split(X, y, g)`: 나누는 방법 5가지를 차례로 내놓는다. `next(...)`는 그중 **첫 번째 하나만** 꺼낸다.
- **위치(position)와 행 번호(index)의 차이**
  - `split()`이 돌려주는 값은 "train 안에서 몇 번째인가"라는 **위치**(0, 1, 2, …)다.
  - 우리에게 필요한 것은 `df`의 **행 번호**다. train 행의 행 번호는 0, 2, 4, …처럼 띄엄띄엄 있다.
  - `train_idx[fit_pos]`로 위치를 행 번호로 바꾼다. 이걸 빠뜨리면 엉뚱한 행을 가져온다. 자주 하는 실수다.

**클래스 개수 출력**

- `reindex(LABELS)`: 행 순서를 `LABELS` 순서(정상 → 미충전 → …)로 맞춘다.

## 단계 5. 베이스라인 학습

### 큰 그림: 이 단계에서 하는 일
4단계에서 만든 **학습용 4,219행**을 모델에게 보여 주고, "이런 공정 조건이면 이런 불량"이라는 규칙을 배우게 한다. 이것을 **학습(fit)**이라고 한다.

| | 내용 |
|---|---|
| 입력 | 학습용 행의 피처 21개 (`X.loc[fit_idx]`)와 정답 (`df.loc[fit_idx, "label"]`) |
| 출력 | 학습이 끝난 모델 `model`. 새 샷의 피처를 넣으면 7종 중 하나를 답한다 |

이번 모델은 **로지스틱 회귀 + class_weight**다. 강사의 공개 기준선(0.2517)과 같은 종류의 모델이라, 우리 코드가 제대로 작동하는지 비교해 볼 수 있다.

### 모델 안에서 일어나는 일: 3단계 컨베이어 벨트
모델에 데이터를 넣으면 세 단계를 차례로 거친다. 이 세 단계를 하나로 묶은 것이 **Pipeline**이다.

```
피처 21개
   │
   ▼
[1] 결측 채우기 (SimpleImputer)     빈칸을 중앙값으로 채운다
   │
   ▼
[2] 크기 맞추기 (StandardScaler)    열마다 단위가 다른 값을 비슷한 크기로 바꾼다
   │
   ▼
[3] 로지스틱 회귀 (LogisticRegression)   7종 중 하나를 고른다
   │
   ▼
예측 라벨
```

### [1] 결측 채우기: 왜 Pipeline 안에 넣나
3단계에서 정한 원칙이다. 결측을 채울 중앙값은 **학습용 데이터에서만** 계산해야 한다. 검증용 데이터의 값이 섞이면 정보 유출이다.

Pipeline에 넣으면 이 원칙이 자동으로 지켜진다.
- `model.fit(학습용)`을 하면 → 학습용에서 중앙값을 **계산하고 기억한다**
- `model.predict(검증용)`을 하면 → 기억해 둔 값으로 **채우기만 한다** (다시 계산하지 않음)

### [2] 크기 맞추기: 왜 필요한가
피처마다 단위와 크기가 완전히 다르다.

| 피처 | 평균 | 범위 |
|---|---|---|
| Casting_Pressure (주조압) | 859 | 516 ~ 1,164 |
| Cycle_Time (사이클 시간) | 27.7 | 20.2 ~ 218.6 |
| Velocity_1 (속도) | 0.148 | 0.136 ~ 0.180 |

로지스틱 회귀는 "피처 × 가중치"를 더해서 판단한다. 숫자 크기가 이렇게 다르면 두 가지 문제가 생긴다.
1. **학습이 잘 끝나지 않는다.** 모델은 가중치를 조금씩 고쳐 가며 정답에 가까워지는데, 크기가 제각각이면 어떤 가중치는 크게, 어떤 가중치는 아주 작게 고쳐야 해서 갈피를 못 잡는다.
2. **작은 숫자 피처가 불리하다.** 로지스틱 회귀는 가중치가 너무 커지지 않게 막는 장치(규제)가 기본으로 켜져 있다. 속도처럼 값이 0.1대인 피처는 영향을 주려면 큰 가중치가 필요한데, 그 장치에 막혀서 제대로 쓰이지 못한다.

**StandardScaler**는 열마다 `(값 − 평균) ÷ 표준편차`를 계산한다. 그러면 모든 피처가 "평균 0, 퍼짐 정도 1"인 비슷한 크기가 된다. 이 평균과 표준편차도 **학습용에서만 계산**해야 하므로 Pipeline 안에 넣는다.

> 트리 모델(랜덤포레스트)은 "값이 600보다 큰가?"처럼 기준선만 긋기 때문에 크기 맞추기가 필요 없다. 로지스틱과 MLP에는 필요하다.

### [3] 로지스틱 회귀: 설정 2가지
| 설정 | 값 | 의미 |
|---|---|---|
| `class_weight` | `"balanced"` | 개수가 적은 불량 클래스를 틀리면 벌점을 크게 준다 (기타불량 1건 ≈ 정상 54건) |
| `max_iter` | `1000` | 가중치를 고치는 작업을 최대 몇 번 반복할지 |

**`max_iter`를 1000으로 올린 이유**
기본값은 100회다. 실제로 돌려 보니 이 데이터는 **249회** 만에 학습이 끝났다. 100회로 두면 학습이 끝나기 전에 멈추고 `ConvergenceWarning`(수렴 경고: 아직 덜 배웠다는 경고)이 뜬다. 넉넉하게 1,000회로 두면 249회에서 스스로 멈춘다.

### 미리 해 본 실험: 각 부품을 빼면 어떻게 되나
검증용 1,055행으로 macro F1을 쟀다.

| 구성 | macro F1 | 무슨 일이 일어났나 |
|---|---|---|
| **결측 채우기 + 크기 맞추기 + class_weight** | **0.239** | 이번 모델 |
| 크기 맞추기를 뺌 | 0.192 | 1,000회를 반복해도 학습이 끝나지 않음 (수렴 경고) |
| class_weight를 뺌 | 0.125 | 검증용 1,055행 중 **1,054행을 "정상"이라고 답함**. 전부 정상으로 찍은 점수(0.1248)와 같음 |

- class_weight가 없으면 모델은 "다 정상이라고 하면 77%는 맞는다"를 배우고 불량을 포기한다. **이 데이터에서는 class_weight가 가장 중요한 부품이다.**
- 강사의 공개 기준선 표(기본 로지스틱 0.1313 → class_weight 로지스틱 0.2517)와 같은 현상이 우리 실험에서도 나왔다.
- 우리 점수 0.239가 공개 기준선 0.2517보다 조금 낮은 것은 이상하지 않다. 채점 데이터가 다르고(우리는 검증용, 강사는 public), 검증용 소수 클래스가 15~20건뿐이라 몇 건 차이로도 점수가 흔들린다.

### 선택지
| 부품 | 다른 방법 | 이번 선택 이유 |
|---|---|---|
| 결측 채우기 | 평균, 앞 샷 값 | 중앙값: 이상값에 덜 흔들림. 나중에 데이터 파트 결정으로 교체 |
| 크기 맞추기 | MinMaxScaler (0~1로 맞춤) | StandardScaler: 가장 흔한 기본. MinMax는 Cycle_Time 218.6 같은 이상값 하나에 나머지 값이 한쪽으로 몰림 |
| 불균형 처리 | 소수 클래스 복제(오버샘플링), 임계값 조정 | class_weight: 설정 한 줄로 끝나고 데이터를 바꾸지 않음 |
| 모델 | 랜덤포레스트, MLP | 로지스틱: 공개 기준선과 같은 모델이라 비교 기준으로 좋음. 나머지는 10/20 단계 |

### 코드

**① import 추가** (라이브러리 영역, `StratifiedGroupKFold` 아래)
```python
from sklearn.impute import SimpleImputer
from sklearn.linear_model import LogisticRegression
from sklearn.pipeline import Pipeline
from sklearn.preprocessing import StandardScaler
```

**② 설정 영역에 추가**
```python
CLASS_WEIGHT = "balanced"   # 소수 클래스를 틀리면 벌점을 크게 (None으로 바꾸면 끔)
MAX_ITER = 1000             # 학습 반복 최대 횟수 (기본 100회로는 학습이 덜 끝남)
```

**③ `build_model()` 함수 교체**
```python
def build_model():
    """[5단계] 학습할 모델을 만든다.

    결측 채우기 → 크기 맞추기 → 로지스틱 회귀를 하나로 묶는다(Pipeline).
    묶어 두면 중앙값·평균 같은 값이 학습용 데이터에서만 계산된다.
    """
    model = Pipeline([
        ("imputer", SimpleImputer(strategy="median")),
        ("scaler", StandardScaler()),
        ("clf", LogisticRegression(class_weight=CLASS_WEIGHT, max_iter=MAX_ITER)),
    ])
    return model
```

**④ `main()`에 추가** (4단계 아래)
```python
    model = build_model()                                    # 5단계
    model.fit(X.loc[fit_idx], df.loc[fit_idx, TARGET_COL])
    n_iter = model.named_steps["clf"].n_iter_[0]
    print(f"[5단계] 학습 완료: 학습용 {len(fit_idx)}행 (반복 {n_iter}회 / 최대 {MAX_ITER}회)")
```

### 코드 설명 (입력 → 출력 중심)

**`build_model()`**
| | 내용 |
|---|---|
| 입력 | 없음 |
| 출력 | 아직 아무것도 배우지 않은 빈 모델 (부품 3개가 연결된 상태) |

- `Pipeline([...])`: 부품을 순서대로 적은 목록을 받는다. 각 부품은 `("이름", 부품)` 형태다.
- 이름(`"imputer"`, `"scaler"`, `"clf"`)은 나중에 부품을 하나 꺼내 볼 때 쓴다. `clf`는 classifier(분류기)의 줄임말로 관례적으로 많이 쓰는 이름이다.
- `strategy="median"`: 중앙값으로 채우라는 설정

**`model.fit(X.loc[fit_idx], df.loc[fit_idx, TARGET_COL])`**
| | 내용 |
|---|---|
| 입력 | 학습용 4,219행의 피처 (문제지)와 정답 (답안지) |
| 하는 일 | [1] 중앙값 계산·기억 → [2] 평균·표준편차 계산·기억 → [3] 가중치 학습 |
| 출력 | 따로 돌려주지 않는다. `model` 자체가 "학습된 모델"로 바뀐다 |

- `X.loc[fit_idx]`: 4단계에서 받은 학습용 행 번호 명단으로 `X`에서 해당 행만 꺼낸다.
- `df.loc[fit_idx, TARGET_COL]`: 같은 명단으로 정답 열만 꺼낸다. `X`와 `df`는 행 순서가 같아서 같은 명단으로 꺼내면 줄이 맞는다 (3단계에서 행을 건드리지 않은 이유).
- scikit-learn의 모든 모델은 **`fit(문제, 정답)`으로 배우고 `predict(문제)`로 답한다.** 로지스틱이든 랜덤포레스트든 이 두 가지 사용법이 같다. 그래서 나중에 모델을 바꿀 때 `build_model()` 안쪽만 바꾸면 된다.

**`model.named_steps["clf"].n_iter_[0]`**
- `named_steps["clf"]`: Pipeline에서 `"clf"`라는 이름의 부품(로지스틱 회귀)을 꺼낸다.
- `n_iter_`: 실제로 몇 번 반복하고 학습을 끝냈는지 기록된 값이다. 끝에 `_`가 붙은 속성은 "학습한 뒤에 생기는 값"이라는 scikit-learn의 관례다.
- 이 숫자가 `MAX_ITER`(1000)와 같으면 학습이 덜 끝났다는 뜻이다. 그래서 출력해서 확인한다.

### 정리
- 모델 = **결측 채우기 → 크기 맞추기 → 로지스틱 회귀**를 묶은 Pipeline
- Pipeline은 중앙값·평균·표준편차를 **학습용에서만 계산**하게 해서 정보 유출을 막는다.
- 크기 맞추기가 없으면 학습이 끝나지 않는다 (0.192). class_weight가 없으면 전부 정상이라고 답한다 (0.125).
- scikit-learn 모델은 모두 `fit(문제, 정답)` / `predict(문제)`로 쓴다 → 모델 교체는 `build_model()`만 바꾸면 된다.
- **구술 대비:** "class_weight를 바꾸면 뭐가 달라집니까?" → "class_weight를 끄면 검증용 1,055샷 중 1,054샷을 정상이라고 답해서 불량을 거의 하나도 못 잡습니다. 켜면 소수 불량을 틀릴 때 벌점이 커져서 불량을 찾으려고 합니다."
- **현장 수정 대비:** `CLASS_WEIGHT = None`으로 바꾸고 다시 돌리면 위 실험을 그 자리에서 보여 줄 수 있다.

### 하는 일
학습된 모델로 검증용 1,055행의 정답을 예측하고, 실제 정답과 비교해 채점한다.

| | 내용 |
|---|---|
| 입력 | 검증용 정답 `y_true`, 모델의 예측 `y_pred` (둘 다 1,055개) |
| 출력 | macro F1 점수 1개 + 클래스별 성적표 + 혼동행렬 (화면 출력) |

### 개념
- **precision(정밀도)**: 모델이 "A"라고 답한 것 중 진짜 A의 비율. 낮으면 헛경보가 많다
- **recall(재현율)**: 진짜 A 중 모델이 찾아낸 비율. 낮으면 놓치는 게 많다
- **F1**: precision과 recall의 조화평균. 둘 다 높아야 높다
- **macro F1**: 7클래스 F1의 단순 평균 (대회 채점 기준)
- **혼동행렬**: 행 = 실제 정답, 열 = 모델 예측. 대각선이 맞힌 개수, 나머지는 "무엇을 무엇으로 착각했나"

### 코드
```python
# ① import
from sklearn.metrics import classification_report, confusion_matrix, f1_score

# ② 설정
PUBLIC_BASELINE = 0.2517  # 강사 공개 기준선 (로지스틱 + class_weight, public 점수)

# ③ evaluate()
def evaluate(y_true, y_pred):
    """[6단계] 검증 점수를 계산하고 출력한다."""
    score = f1_score(y_true, y_pred, labels=LABELS, average="macro", zero_division=0)

    print(f"[6단계] 검증 macro F1 = {score:.4f} (공개 기준선 {PUBLIC_BASELINE})")
    print(classification_report(y_true, y_pred, labels=LABELS, digits=3, zero_division=0))

    cm = confusion_matrix(y_true, y_pred, labels=LABELS)
    short = [name.replace("불량_", "") for name in LABELS]
    cm_table = pd.DataFrame(cm, index=short, columns=short)
    print("혼동행렬 (행 = 실제, 열 = 예측)")
    print(cm_table.to_string())
    return score

# ④ main()에 추가
    valid_pred = model.predict(X.loc[valid_idx])  # 6단계
    evaluate(df.loc[valid_idx, TARGET_COL], valid_pred)
```

## 단계 8. 검증 강화: 5조각 교차검증 (10/19)

### 하는 일
- 지금까지는 `next(sgkf.split(...))`로 **5조각 중 첫 번째만** 써서, 학습 80% / 검증 20%로 한 번만 나눈 것이었다.
- 이제 5조각이 **한 번씩 돌아가며** 검증용이 되도록 바꾼다 → 5번 학습, 5번 예측.
- 검증용 소수 클래스가 15~20개뿐이라 한 번 나누기 점수는 운이 섞인다. 모델을 비교하기 전에 기준부터 튼튼하게 만든다.

### 개념: 점수를 모으는 두 방법
| | A. 조각별 점수 평균 | B. 예측을 합쳐서 한 번 채점 (선택) |
|---|---|---|
| 대표 점수 | 조각별 F1 5개의 평균 | 5번의 검증 예측(= train 5,274개 전체)을 합쳐 F1 한 번 계산 |
| 흔들림(±) | 보임 | 보임 (조각별 점수도 같이 출력) |
| 리포트·혼동행렬 | 5개로 흩어짐 | 1개 |
| 소수 클래스 | 조각마다 3~5개라 F1이 튐 (0.00이 나오기도) | 개수를 먼저 다 더한 뒤 계산 → 안정적 |

- **oof(out-of-fold) 예측** = "그 행을 학습에 안 쓴 모델이 낸 예측". 5바퀴 돌면 train 모든 행이 하나씩 갖게 된다.
- 핵심은 **모델을 비교할 때 계속 같은 방식을 쓰는 것**.

### StratifiedGroupKFold 정리
- 재료: `split(X, y, groups)` → X는 행 개수만 봄, y로 비율 맞춤, groups로 쌍둥이 묶음
- 결과: **generator** (달라고 할 때마다 (학습용, 검증용) 쌍을 하나씩, 총 5번). 한 번 다 꺼내면 비므로 리스트(`folds`)에 옮겨 담아 둔다
- 돌려주는 것은 **순서 번호(pos)** → `train_idx[pos]`로 **행 번호(idx)**로 바꿔서 쓴다
- 동작: 그룹을 쪼갤 수 없는 덩어리로 보고(→ 쌍둥이 안 갈라짐), 덩어리마다 "넣었을 때 클래스 비율이 가장 고른 조각"에 넣는다(→ 비율 맞춤)
- 쌍둥이 그룹 번호(`make_twin_groups`)는 **전체 7,535행**에 붙는다. 일반 행은 1씩 늘고, 쌍둥이 두 번째 행만 앞 행 번호를 물려받는다 (`(~same_as_prev).cumsum()`)

### 코드에서 바뀐 곳
| 곳 | 바뀐 내용 |
|---|---|
| 설정 | `VALID_FOLDS` 주석만 수정 (값은 5 그대로) |
| `split_validation` | `next(...)` → `for k, (fit_pos, valid_pos) in enumerate(sgkf.split(...), start=1)`. 5쌍을 `folds` 리스트로 반환. "모든 train 행이 정확히 한 번씩 검증용" assert 추가 |
| `cross_validate` (새 함수) | 빈 답안지 `oof_pred` → 조각마다 **새 모델** 학습·예측 → 검증 칸만 채움. 조각별 F1과 평균 ± 표준편차 출력 |
| `evaluate` | 출력 문구만 "합쳐서 채점한 macro F1" |
| `main` | `folds = split_validation(...)` → `oof_pred, fold_scores = cross_validate(...)` → `evaluate(정답, oof_pred)`. 7단계는 그대로 |

### 구술 대비
- "왜 교차검증?" → 검증용 소수 클래스가 15~20개뿐이라 한 번 나누면 운이 섞임. 실제로 한 번 나누기 0.239 vs 교차검증 0.226

## 단계 9. class_weight 강도 실험 (10/19 시작, 10/21 완료)

### 하는 일
- `class_weight="balanced"`는 너무 세서 정상의 77%를 불량이라고 불렀다 (정상 recall 0.235).
- 가중치를 `balanced ** 강도`로 약하게 만들고, 강도를 여러 개 바꿔 가며 5조각 교차검증으로 비교한다.

- 조각마다 **그 조각의 학습용 정답만**으로 가중치를 계산 → 검증용 정보 유출 방지 (그래서 조각마다 가중치가 조금씩 다름)

### 결정: 강도 0.5
1. 점수가 같으면 헛경보가 적은 쪽 (재검사 부담: 정상의 21% vs 31%)
2. "balanced의 제곱근"으로 한 문장 설명 가능

- `main.py` 실행: 합쳐서 macro F1 **0.2896** (실험 파일과 동일) → **새 기준선**. 공개 기준선 0.2517 (public 점수라 참고만)

### 구술 대비
- "왜 0.5?" → 교차검증에서 0.5·0.6이 0.290으로 공동 1위, 차이는 흔들림보다 작음. 같은 점수면 헛경보가 적은 0.5

| ④ | 검사 코드가 지운 함수와 함께 사라짐 | `check_data(data)` 추가: 행 수, 열 일치, 식별 열·그룹 번호 없음, 라벨 7종 |
| ⑤ | 안 쓰는 설정 | 경로·`CONSTANT_COLS`·`N_TOTAL` 삭제, `EXTRA_DROP_COLS` → `DROP_COLS = ()`를 `load_data(drop_cols=...)`에 넘김 |

- 로컬 `학생배포/`는 git이 아님 → 저장소에서 pull 후 `preprocess.py`를 **그대로 복사** (팀원이 고치면 다시 복사)
- 데이터 CSV 크기가 저장소와 다른 건 줄바꿈(CRLF) 차이. 내용은 같음

### HGB 추가 (`MODEL_NAME = "hgb"`)
- `HistGradientBoostingClassifier(class_weight="balanced", max_leaf_nodes=15, learning_rate=0.05, max_iter=100, random_state=SEED)`
- **주의:** HGB는 라벨을 내부에서 숫자로 바꾼 뒤 가중치를 찾아서 글자 키 사전(`make_class_weight`)을 넣으면 에러 → balanced 고정 (sample_weight로 강도 0.5·0.75를 넣어 봐도 0.300·0.298로 나아지지 않음)
- 7단계 출력: hgb면 "class_weight balanced", 아니면 "class_weight 강도 0.5"
