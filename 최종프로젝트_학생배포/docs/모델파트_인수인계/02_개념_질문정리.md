## 1. 정밀도, 재현율, F1, macro F1

### 정밀도와 재현율
미충전 불량을 찾는 상황을 예로 든다.

- **정밀도(Precision)** = 모델이 "미충전"이라고 한 것 중 진짜 미충전의 비율
  - "경보가 울렸을 때 그 경보를 믿어도 되는가"
  - 정밀도가 낮으면 헛경보가 많다.
- **재현율(Recall)** = 진짜 미충전 중에서 모델이 찾아낸 비율
  - "불량을 얼마나 빠뜨리지 않고 잡는가"
  - 재현율이 낮으면 놓치는 불량이 많다.

예: 진짜 미충전 100건, 모델이 "미충전"이라고 한 것 80건, 그중 진짜 60건
- 정밀도 = 60 / 80 = 0.75 (경보 4번 중 3번이 진짜)
- 재현율 = 60 / 100 = 0.60 (불량 10건 중 6건을 잡음)

두 지표는 한쪽을 올리면 다른 쪽이 내려간다. 경보를 많이 울리면 덜 놓치지만 헛경보가 늘어난다. 그래서 둘을 하나로 합친 점수인 F1을 쓴다.

### 조화평균과 F1
> **F1 = 2 × 정밀도 × 재현율 ÷ (정밀도 + 재현율)**

"재현율/정밀도"가 아니다. 위 식이 정밀도와 재현율의 **조화평균**이다. 조화평균은 **둘 중 작은 값에 끌려가는 평균**이다.

| 정밀도 | 재현율 | 산술평균 | 조화평균 (F1) |
|---|---|---|---|
| 0.8 | 0.8 | 0.80 | 0.80 |
| 1.0 | 0.1 | 0.55 | **0.18** |

두 번째 줄은 "확실할 때만 한 번 경보를 울리는 모델"이다. 경보는 정확하지만 불량의 90%를 놓친다. 산술평균은 0.55로 괜찮아 보이지만 F1은 0.18이다. **F1은 둘 다 높아야만 높다.**

### 그냥 F1과 macro F1
- **그냥 F1**은 클래스 하나에 대한 점수다 (예: 미충전 F1).
- 이번 과제는 클래스가 7개라 F1도 7개 나온다.
- **macro F1** = 7개 클래스 F1을 **똑같은 비중으로 단순 평균**한 값

**전부 "정상"으로 찍으면**
- 정확도는 77.6%로 좋아 보인다.
- macro F1은 정상 F1 약 0.87, 나머지 6개는 0 → (0.87 + 0 × 6) ÷ 7 = **0.1248**

→ 76건뿐인 기타불량도 4,092건인 정상과 똑같이 점수의 1/7을 차지한다. **작은 불량 클래스를 잘 맞히는 것이 점수에 결정적이다.**

## 2. 공개 기준선 0.2517, class_weight

### 공개 기준선
강사가 미리 돌려 본 간단한 모델의 점수다. **이 점수를 넘지 못하면 리더보드에 올라가지 못한다** (최소 합격선).

| 방법 | macro F1 |
|---|---|
| 전부 "정상" | 0.1248 |
| 로지스틱 회귀 (기본) | 0.1313 |
| 로지스틱 회귀 + class_weight | **0.2517** ← 기준선 |

### class_weight
기본 설정에서는 모든 샷이 틀렸을 때 받는 벌점이 똑같다. 정상이 압도적으로 많으니 모델은 "일단 정상이라고 하면 대부분 맞는다"를 배우고 소수 불량을 무시한다.

**class_weight는 클래스마다 틀렸을 때의 벌점 크기를 다르게 주는 설정이다.** `class_weight='balanced'`는 개수가 적은 클래스일수록 벌점을 크게 준다.

| 클래스 | 개수 | 벌점 가중치 |
|---|---|---|
| 정상 | 4,092 | 약 0.18 |
| 기타불량 | 76 | 약 9.9 |

기타불량 1건을 틀리면 정상 약 54건을 틀린 것과 같은 벌점을 받는다.

기본 로지스틱(0.1313)은 전부 정상(0.1248)과 거의 같다. class_weight 하나로 0.2517까지 오른다. → **이 데이터는 클래스 불균형을 어떻게 다루느냐가 핵심이다.**

## 3. public과 private

| 구분 | 샷 수 | 정답 공개 | 용도 |
|---|---|---|---|
| train | 5,274 | 공개 | 학습용 |
| public | 1,130 | 비공개 | 중간 점수 확인 (팀당 10회) |
| private | 1,131 | 비공개 | 최종 채점 (발표 당일 1회) |

- 제출은 public + private 2,261샷을 한 파일로 낸다. 어느 샷이 public인지는 강사만 안다.
- **public은 validation과 비슷하지만 같지 않다.** validation은 우리가 직접 떼어 낸 데이터라 정답을 알고 마음대로 분석할 수 있다. public은 점수 하나만 받고 횟수 제한이 있다.
- public 점수로 모델을 고르면 안 된다. 10번 중 가장 높은 모델은 실제로 좋은 게 아니라 public과 우연히 잘 맞았을 수 있다. 그러면 private에서 점수가 떨어진다.
- **모델 선택은 validation으로, public은 제출 파일 작동 확인과 대략적인 수준 확인용으로만 쓴다.**

## 4. shot_id, id, Shot 사용 금지의 의미

번호지만 **이 데이터에서는 쓰면 실제로 점수가 오른다.** 그래서 따로 금지했다.

**이유 1: 번호가 생산 시기를 알려 준다**
- shot_id는 생산 순서다. 불량은 특정 시기에 몰려 있다 (기공 233건 중 232건이 뒤쪽 40%).
- 모델이 "shot_id가 4,500보다 크면 기공"을 배운다. public/private이 train 사이사이에 섞여 있어서 리더보드에서는 잘 맞는다.
- 하지만 내일 생산하는 샷은 새 번호를 받는다. 공정 조건이 아니라 "언제 생산됐는지"를 외운 것이라 현장에서 쓸모없다.

**이유 2: 앞뒤 샷의 정답을 베낄 수 있다**
- public 샷 2번 앞뒤는 train 샷 1번, 3번이다. 이 정답은 우리가 안다.
- 불량은 연달아 나온다 (앞 샷이 불량이면 다음 샷 불량률 53%, 정상이면 14%).
- 옆 샷 정답을 베끼기만 해도 점수가 꽤 나온다. 이것이 "앞뒤 샷의 정답을 끌어다 쓰면 실격"의 뜻이다.

→ 번호는 **정렬할 때만** 쓰고 모델 입력으로는 넣지 않는다. 참고로 `id = (shot_id − 1) × 1000 + Shot`이라 새로운 정보가 없다.

## 5. 원본불량기록 파일을 쓸 수 없는 이유, 라벨 재생성

이 파일은 **공식 정답이 아니라**, 공식 정답(7종)을 만들기 전의 **공장 검사 원본 기록**이다.

| 파일 | 형태 |
|---|---|
| 원본불량기록 | 불량 13종마다 열이 따로 있음. 한 샷에 불량 2~3개가 동시에 표시되기도 함 |
| 정답_train | 위 기록을 정리해서 샷마다 라벨 하나로 만든 것 |

**1) 피처로 쓰기 금지:** 검사 결과, 즉 사실상 정답이다. 그리고 train에만 있어서 예측할 때는 넣을 값이 없다.

**2) 라벨 재생성 금지:** 라벨 재생성은 원본 기록으로 **우리만의 규칙으로 정답을 다시 만드는 것**이다 (예: "미충전+얼룩이면 얼룩으로 하자"). 채점은 공식 정답 기준이라 점수가 떨어진다.

→ 용도는 **"라벨이 어떻게 만들어졌는지 읽고 생각하는 것"**. 보고서와 구술에서 묻는다.

## 6. 데이터 메모

데이터를 열어 보고 **이상한 점, 특징, 중요한 사항을 기록한 메모**다.
- 예: "이 열은 값이 하나뿐이다", "이 구간에 결측이 90개 있다", "같은 샷이 두 번 기록된 것 같다"
- 데이터 담당자가 주로 쓰지만 보고서 1번과 발표 3번 슬라이드의 재료라 팀 전체 자료다.
- 같은 날의 "첫 제출 1회"는 모델 파트 몫이다. 성능과 상관없이 제출 과정이 작동하는지 미리 확인한다.

## 7. 로지스틱, RF(랜덤포레스트), MLP

세 가지는 **같은 계열이 아니라 서로 완전히 다른 방식의 모델**이다. 입력과 출력은 같고 방식이 다르니 결과도 다르다. 그래서 비교한다.

### 로지스틱 회귀 (Logistic Regression)
1. 입력값에 가중치를 곱해서 더한다 (예: `0.3×주조압 − 0.5×속도 + …`). 선형 계산이다.
2. 결과를 확률로 바꾼다. 클래스가 7개라 softmax로 7개 확률을 낸다.
3. 확률이 가장 높은 클래스를 답으로 고른다.

단순하다. "주조압이 높을수록 불량"처럼 한 방향 관계는 잘 잡지만, "주조압이 특정 범위일 때만 불량" 같은 복잡한 관계는 잘 못 잡는다.

### RF (Random Forest, 랜덤포레스트)
RF와 랜덤포레스트는 같은 것이다.

**결정나무(Decision Tree)**는 스무고개처럼 질문을 이어 가며 답을 찾는다.
```
제품 유형이 2인가?
├─ 예 → 주조압이 600보다 낮은가?
│        ├─ 예 → 기공
│        └─ 아니오 → 정상
└─ 아니오 → 속도가 0.15보다 낮은가? → …
```
**랜덤포레스트**는 이런 나무를 수백 개 만들고 다수결로 답을 정한다. 나무마다 학습 데이터 일부와 입력 열 일부를 무작위로 줘서 조금씩 다르게 자란다. 나무 하나는 실수가 잦지만 다수결은 안정적이다.

### MLP (Multi-Layer Perceptron, 다층 퍼셉트론)
신경망(딥러닝)의 가장 기본 형태다.
- 구조: `입력 → [선형 계산 → 활성화 함수] → [선형 계산 → 활성화 함수] → 출력`
- **층 사이에 활성화 함수(ReLU 등)가 반드시 들어가야 한다.** 없으면 선형 계산 여러 번 = 선형 계산 한 번이 되어 로지스틱과 같아진다.
- 활성화 함수 덕분에 복잡한 관계를 잡을 수 있다.

### 비교
| 모델 | 방식 | 특징 |
|---|---|---|
| 로지스틱 | 입력값을 가중치로 더함 | 가장 단순, 해석 쉬움 |
| RF | 나무 수백 개의 다수결 | 표 데이터에 강함, 설정을 덜 만져도 잘 됨 |
| MLP | 신경망 | 가장 유연함, 설정할 것이 많고 데이터가 적으면 불리 |

과제 흐름: 로지스틱·RF로 기준 → MLP 설계 → 비교 → **어느 쪽이 이기든 이유를 데이터 특성으로 설명**. MLP가 반드시 이겨야 하는 것은 아니다.

## 8. 이중기록, 무작위 CV, KNN

### 개수
| 구분 | 개수 |
|---|---|
| 똑같은 행이 2개씩 붙은 쌍 | 2,918쌍 = 5,836행 |
| 단독 행 | 1,699행 |
| 합계 | 7,535행 |

각 쌍은 "원본 1 + 복사본 1"이다. 중복을 지우면 **2,918행이 사라지고 4,617행이 남는다.**

### 실제 예시
```
shot_id      id      Shot  Velocity_1  High_Velocity  Casting_Pressure  Melting_Furnace_Temp
  1100   1099001      1      0.140        2.153            1054              700.4
  1101   1100001      1      0.140        2.153            1054              700.4   ← 위와 같음
  1102   1101002      2      0.142        2.157            1055              702.1
  1103   1102002      2      0.142        2.157            1055              702.1   ← 위와 같음
```

### Shot 번호
설비의 사출 횟수 카운터다 ("이번 생산 회차의 몇 번째 샷").
- **겹쳐도 정상:** 생산을 새로 시작하면 1로 돌아간다 (이 데이터에서 6번). 다른 회차에 "Shot 1"이 각각 있는 것은 자연스럽다.
- **이상한 경우:** 바로 붙은 두 행이 Shot 번호와 공정 값까지 전부 같으면 같은 샷이 두 번 기록된 것으로 보인다. 왜 그런지는 확인이 필요하다.

### id 간격 1000
`id = (shot_id − 1) × 1000 + Shot`이라서 Shot이 1 늘면 id가 1,001 늘고, Shot이 그대로면 1,000 는다. "id 간격 1000" = "Shot 번호가 안 바뀌었다"일 뿐이다.

### 라벨 100% 동일
두 행 모두 train에 있는 1,439쌍은 모두 라벨이 같았다. 같은 샷의 복사본이라는 해석과 맞다.

### 무작위 CV
**CV(교차검증)**: train을 5조각으로 나눠 4조각으로 학습, 1조각으로 채점. 검사 조각을 바꿔 5번 반복하고 평균 낸다.

**무작위 CV**는 조각을 무작위로 나눈다. 쌍둥이 하나는 학습에, 다른 하나는 검사에 들어갈 수 있다. → 시험 문제를 미리 본 상태라 점수가 실제보다 높게 나온다.

### KNN과 RF가 public에서 유리한 이유
**KNN(K-최근접 이웃)**: 새 샷과 공정 값이 가장 비슷한 train 샷 K개를 찾아 그 정답으로 다수결하는 모델.

KNN과 RF는 **학습 데이터를 거의 그대로 기억하는 능력**이 강하다. public/private 중 약 1,207샷은 쌍둥이가 train에 있다. 공정 조건을 이해하지 않아도 기억한 정답을 꺼내면 맞힌다. → 리더보드 점수는 높지만 현장의 새 샷에는 쌍둥이가 없어서 현장 성능을 반영하지 않는다. 규칙 위반 여부가 애매해서 강사 확인이 필요하다.

## 9. 상수열

**모든 행에서 값이 똑같은 열**이다. 이 데이터에는 8개가 있다.

| 열 | 값 |
|---|---|
| Air_Pressure_Min / Max | 3 / 9 |
| Coolant_Temp_Min / Max | 10 / 50 |
| Factory_Temp_Min / Max | 18 / 22 |
| Factory_Humidity_Min / Max | 18 / 22 |

**제거 이유:** 모델은 "값이 다르면 결과도 다르다"는 패턴을 배운다. 정상이든 불량이든 3인 값으로는 둘을 구분할 수 없어서 빼도 손해가 없다.

## 12. 그룹 분할, GroupKFold

**그룹 분할**: 학습용과 검증용으로 나눌 때 **같은 그룹의 행은 반드시 같은 쪽에 들어가게** 나누는 방법. 이 데이터에서는 쌍둥이 두 행을 한 그룹으로 묶는다.

```
무작위 분할:  [쌍A-1] → 학습      [쌍A-2] → 검증   ✗ 정답 유출
그룹 분할:    [쌍A-1, 쌍A-2] → 둘 다 검증          ✓ 공정한 시험
```

**GroupKFold**: scikit-learn 기능. 5조각 교차검증을 하면서 그룹이 쪼개지지 않게 자동으로 나눠 준다. 그룹 번호만 알려 주면 된다.

## 18. softmax

**클래스마다 점수를 하나씩 받아서 확률로 바꾸는 함수**. 바꾼 확률은 모두 0~1이고 다 더하면 1이다.

### 왜 필요한가
모델 마지막 단계는 클래스마다 점수를 낸다 (7종이면 7개). 이 점수는 3.2, −1.5처럼 크기 제한이 없어서 확률로 읽을 수 없다. softmax가 "정상 66%, 미충전 24%, …"로 바꿔 준다.

### 계산 방법
1. 각 점수에 지수함수(e^x)를 씌운다. 음수도 양수가 되고 큰 점수는 더 크게 벌어진다.
2. 그 값들을 모두 더한다.
3. 각 값을 합으로 나눈다. → 전체 합이 1

| 클래스 | 점수 | e^점수 | ÷ 합(11.21) = 확률 |
|---|---|---|---|
| 정상 | 2.0 | 7.39 | **0.66** |
| 미충전 | 1.0 | 2.72 | **0.24** |
| 기공 | 0.1 | 1.11 | **0.10** |
| 합계 | | 11.21 | 1.00 |

점수 순서는 유지된다. 답은 확률이 가장 높은 **정상**.

### sigmoid와의 차이
| 함수 | 쓰는 경우 | 출력 |
|---|---|---|
| sigmoid | 두 가지 중 하나 (불량인가 아닌가) | 확률 1개 |
| softmax | 여러 가지 중 하나 (7종 중 무엇인가) | 확률 여러 개, 합 1 |

클래스 2개에서 softmax = sigmoid. softmax는 sigmoid의 다중 클래스 확장이다.

### 이 프로젝트에서 쓰이는 곳
1. **로지스틱 회귀:** 7종 분류에서 내부적으로 softmax를 쓴다 (scikit-learn이 자동 처리).
2. **MLP:** 마지막 층이 점수 7개를 내고 softmax가 확률로 바꾼다. PyTorch의 `CrossEntropyLoss`는 softmax를 내부에 포함한다. → **모델 마지막 층에 softmax를 따로 넣지 않는 것이 일반적이다** (헷갈리기 쉬운 부분).
3. **Q2 운영 기준:** 기본은 확률이 가장 높은 클래스를 고른다. 운영안에서는 "정상 확률이 80% 아래면 경보"처럼 기준을 바꿔 가며 놓침·헛경보를 셀 수 있다. 이때 softmax 확률을 쓴다.

## 19. import는 어디에 쓰나 (torch를 함수 안에서 import한 이유)

- **정석은 파일 맨 위에 모아서 import하는 것이다** (파이썬 공식 스타일 가이드 PEP 8). 이 파일이 무엇에 의존하는지 한눈에 보이고, 라이브러리가 없으면 시작하자마자 오류가 나서 문제를 빨리 알 수 있다.
- 함수 안에서 `try / except ImportError`로 import하는 것은 **"있으면 쓰고 없어도 돌아가야 하는" 선택적 라이브러리**에 쓰는 방식이다.
- 지금 torch를 함수 안에 둔 이유는 **이 컴퓨터에 PyTorch가 설치되어 있지 않아서**다. 맨 위에 `import torch`를 쓰면 1~7단계 코드가 torch를 전혀 안 쓰는데도 실행이 멈춘다.
- 하지만 이 프로젝트에서 torch는 선택이 아니다. MLP 단계부터는 반드시 필요하다. 그래서 **임시 조치**다.
- **할 일:** 가상환경을 만들고 torch를 설치하면 `import torch`를 맨 위로 옮기고 `try / except`를 없앤다. `set_seed()` 안에는 `torch.manual_seed(seed)` 한 줄만 남긴다.

- 이 검사가 있으면 그 자리에서 멈추고 "전처리 중에 행 수가 바뀜"이라고 알려 준다.

**② 식별 열이 피처에 없음**

- 사고 예시 2: 데이터에 `"N/A"` 같은 문자가 섞인 열이 생겼다. 5단계에서 이해하기 어려운 오류가 나는 대신, 여기서 원인을 바로 알려 준다.
- 코드 해설: `all(조건 for c in X.columns)`는 "모든 열 c에 대해 조건이 참인가"를 검사한다. 하나라도 거짓이면 전체가 거짓이다.

## 22. 0보다 큰 열만 고르는 방법 (불리언 인덱싱)

```python
n_missing = X.isna().sum()
n_missing[n_missing > 0].to_dict()
```

**1) `X.isna()`: 칸마다 결측이면 True, 아니면 False인 표**
```
      Velocity_1  Factory_Temp  Factory_Humidity
6915       False          True              True
6916       False          True              True
```

**2) `.sum()`: 열마다 True의 개수를 센다** (True = 1, False = 0으로 더해짐)
```
Product_Type         0
Velocity_1           0
...
Coolant_Pressure     0
Factory_Temp        90
Factory_Humidity    90
```
→ 열 이름이 붙은 숫자 목록(Series)이 된다.

**3) `n_missing > 0`: 각 값이 0보다 큰지 True/False로 바꾼다**
```
Coolant_Pressure    False
Factory_Temp         True
Factory_Humidity     True
```

**4) `n_missing[n_missing > 0]`: True인 자리만 남긴다**
```
Factory_Temp        90
Factory_Humidity    90
```
- 대괄호 안에 True/False 목록을 넣으면 **True인 위치만 골라내는** 기능이다. 이것을 **불리언 인덱싱(boolean indexing)**이라고 한다.
- 2단계의 `df.loc[is_train, ...]`도 같은 원리다 (`is_train`이 True인 행만 고름).

**5) `.to_dict()`: 출력하기 좋게 딕셔너리로 바꾼다** → `{'Factory_Temp': 90, 'Factory_Humidity': 90}`

| | 내용 |
|---|---|
| 입력 | `df` 전체 표 (7,535행) |
| 출력 | `groups` 행마다 그룹 번호 (7,535개, 서로 다른 번호 4,617종류) |

**예시 6행 (실제로는 30개 열을 비교, 여기선 3개만 표시)**
```
shot_id  Shot  Velocity_1  Casting_Pressure   split
 1098    1105    0.142         1039           train
 1099    1106    0.144         1055           private
 1100       1    0.140         1054           train
 1101       1    0.140         1054           private  ← 1100과 같음
 1102       2    0.142         1055           train
 1103       2    0.142         1055           private  ← 1102와 같음
```

| 줄 | 코드 | 입력 → 출력 |
|---|---|---|
| 1 | `input_cols = [...]` | 열 이름 34개 → 비교할 열 30개 (`shot_id`, `id`는 항상 달라서, `split`, `label`은 입력값이 아니라서 뺌. `Shot`은 포함) |
| 2 | `values = df[input_cols].fillna(-1)` | 30개 열 표 → 빈칸을 -1로 채운 표 (NaN끼리는 "다르다"고 판단되므로 비교용으로만 임시로 채움) |
| 3-1 | `values.shift()` | 표 → 한 칸 아래로 민 표 (각 행 자리에 바로 앞 행 값이 옴) |
| 3-2 | `.eq(...)` | 두 표 → 칸마다 같으면 True인 표 |
| 3-3 | `.all(axis=1)` | True/False 표 → 행마다 "전부 True인가" 하나 (True 2,918개) |
| 4-1 | `~` | "앞 행과 같은가" → "새 그룹이 시작되는가"로 뒤집기 |
| 4-2 | `.cumsum()` | True/False → 누적합 = 그룹 번호 |

```
shot_id   앞 행과 같은가   새 그룹 시작?   그룹 번호(누적합)
 1098       False           True            1098
 1099       False           True            1099
 1100       False           True            1100
 1101       True            False           1100  ← 같은 번호
 1102       False           True            1101
 1103       True            False           1101  ← 같은 번호
```
- 번호 자체에는 의미가 없다. 같은 번호끼리 묶인다는 것만 의미가 있다.
- 이 예시에서 1100(train)과 1101(private)이 쌍둥이다 → private 샷의 정답이 train에 그대로 들어 있다. 외우는 모델이 리더보드에서 유리한 이유.

**같은 일을 하는 반복문 버전 (읽기 쉬움, 결과 동일 확인)**
```python
groups = []
group_id = 0
prev_row = None
for row in values.itertuples(index=False):   # 한 행씩 위에서부터 꺼낸다
    if row != prev_row:                       # 앞 행과 다르면
        group_id += 1                         #   새 번호를 만든다
    groups.append(group_id)                   # 지금 번호를 붙인다
    prev_row = row                            # 다음 비교를 위해 기억해 둔다
groups = pd.Series(groups, index=df.index)
```

## 24. split_validation() 흐름

> **한 문장:** train 5,274행을 80%(학습용)와 20%(검증용)로 나눈다. 쌍둥이는 같은 반에, 두 반의 불량 비율은 똑같이.
> (학생을 두 반으로 나눌 때 쌍둥이는 같은 반, 두 반의 남녀 비율은 같게)

| | 내용 |
|---|---|
| 입력 | `df` 전체 표, `groups` 그룹 번호 |
| 출력 | `fit_idx` 학습용 행 번호 4,219개, `valid_idx` 검증용 행 번호 1,055개 |

출력은 데이터가 아니라 **행 번호 명단**이다. 5단계에서 이 명단으로 `X`에서 행을 꺼낸다.

**순서**
1. train 행 번호만 뽑는다 (`train_idx`, 5,274개). 제출 대상은 정답이 없어서 제외
2. 그 행들의 정답(`y`)과 그룹 번호(`g`)를 꺼낸다. 도구가 비율을 맞추려면 정답이, 쌍둥이를 지키려면 그룹 번호가 필요하다
3. 나누기 도구(`StratifiedGroupKFold`)를 설정하고 실행한다. 5가지 나누기 방법 중 첫 번째(`next`)만 받는다. 그룹을 지키면서 비율까지 맞추는 건 직접 짜기 복잡해서 도구를 쓴다
4. 도구가 준 "train 안에서 몇 번째(위치)"를 df의 행 번호로 바꾼다
```
train 안에서 몇 번째:   0   1   2   3  …
df의 행 번호:          0   2   4   5  …   ← "2번째" = df의 4번 행
```
5. 검사: 두 반 합계가 5,274인가 / 두 반에 같은 그룹 번호가 없는가
6. 클래스별 인원을 출력해서 비율(약 20%)을 눈으로 확인한다

### 기억할 것
1. `make_twin_groups()` = 바로 앞 행과 똑같은 행에 같은 번호 → 2,918쌍, 4,617그룹
2. `split_validation()` = 80:20, 쌍둥이는 같은 쪽, 클래스 비율 유지 → 4,219 / 1,055
3. 이유 = 쌍둥이가 갈라지면 모델이 외워서 맞힌다 (RF 0.455 → 0.274)


## 25. "피처 × 가중치의 합"은 로지스틱만의 특징인가?

아니다. **선형 모델 전체의 공통점**이다. 선형 회귀와 로지스틱 회귀는 앞부분이 똑같고 마지막 처리만 다르다.

| 모델 | 1) 점수 계산 (같음) | 2) 마지막 처리 (다름) |
|---|---|---|
| 선형 회귀 | 피처×가중치를 더한 점수 | 점수를 그대로 답으로 (예: 온도 650.3) |
| 로지스틱 회귀 | 피처×가중치를 더한 점수 | 점수를 확률로 바꿔서 분류 (7클래스면 softmax) |

- 로지스틱은 클래스마다 가중치 묶음을 따로 갖는다. 7클래스면 점수 7개를 계산하고, softmax로 확률 7개로 바꾼 뒤 가장 큰 것을 고른다.
- 이름에 "회귀"가 들어 있지만 하는 일은 **분류**다.
- **피처**는 모델에 넣는 입력 항목(열)이다. 예: `Casting_Pressure`. 샷 하나의 실제 숫자(859)는 엄밀히는 "피처 값"이지만 둘 다 "피처"라고 부르는 경우가 많다.

## 26. 가중치가 알아서 맞춰 주면 되지, 크기 차이가 왜 문제인가?

**맞는 직관이다.** "최종 답"만 보면 크기 차이는 문제가 아니다. 속도를 m/s 대신 mm/s로 적으면 값은 1,000배 커지지만, 가중치가 1/1,000이 되면 결과는 똑같다. 문제는 **그 가중치를 찾아가는 과정**에서 생긴다. 두 가지가 있다.

### ① 학습 과정: 조절 폭이 필요와 반대로 나온다
모델은 "가중치를 이쪽으로 조금 움직이면 오차가 줄어든다"는 방향(기울기)을 계산해서 가중치를 고친다. 이때 **움직이는 폭은 피처 값의 크기에 비례**한다.

| 피처 | 값 크기 | 필요한 조절 | 실제로 계산되는 조절 폭 |
|---|---|---|---|
| Casting_Pressure | 약 859 | **작게** (조금만 바꿔도 점수가 크게 변함) | **크게** |
| Velocity_1 | 약 0.148 | **크게** (많이 바꿔야 점수가 겨우 변함) | **작게** |

"크면 크게, 작으면 작게"가 아니라 오히려 **반대**가 필요한데, 계산은 "크면 크게"로 나온다.
- 큰 피처에 맞춰 보폭을 작게 하면 → 작은 피처의 가중치는 거의 안 움직인다 → 반복이 끝없이 길어진다
- 작은 피처에 맞춰 보폭을 크게 하면 → 큰 피처의 가중치가 튀어서 갈피를 못 잡는다

실제 실험: 크기 맞추기를 빼면 **1,000회를 반복해도 학습이 끝나지 않았다** (넣으면 249회).

### ② 규제: 작은 피처가 손해를 본다
로지스틱 회귀에는 "가중치가 너무 크면 벌점"이라는 장치(규제)가 기본으로 켜져 있다(과적합 방지). 이 벌점은 피처의 크기를 모르고 **가중치 크기만** 본다. 값이 작은 피처는 영향을 주려면 큰 가중치가 필요하므로 벌점을 더 많이 받고, 결국 덜 쓰이게 된다.

### 결론
표준화(StandardScaler)로 모든 피처를 "평균 0, 퍼짐 1"로 맞추면 두 문제가 같이 풀린다.
- 모든 가중치가 비슷한 보폭으로 움직여도 된다 → 학습이 빨리 끝난다
- 벌점이 모든 피처에 공평해진다

> 참고: 딥러닝에서 쓰는 **Adam** 같은 학습 방법은 가중치마다 보폭을 따로 조절한다. "각자 맞춰 조절하면 되지 않나"라는 생각을 실제로 구현한 것이다. 그래도 표준화를 같이 하는 것이 기본이다.
> 트리 모델(랜덤포레스트)은 "값이 600보다 큰가?"처럼 기준선만 긋기 때문에 크기와 상관이 없다.

## 27. class_weight가 없으면 왜 전부 "정상"이라고 답하나?

### 모델이 배우는 목표
모델은 **"틀린 정도(손실)의 합계"를 가장 작게** 만드는 가중치를 찾는다. 기본 설정에서는 모든 행이 똑같이 1표다.

train 5,274행 중 정상이 4,092행(77.6%)이다. 게다가 불량 샷의 공정 값은 정상 샷과 많이 겹친다. 예를 들어 비슷한 조건의 샷이 정상 20개, Blow_Hole 2개 섞여 있으면 "정상"이라고 답하는 쪽이 합계 손실이 가장 작다. 이런 일이 거의 모든 구간에서 일어나므로 **"웬만하면 정상"이 모델 입장에서 최선의 답**이 된다.

> 비유: 100문제 중 78문제의 답이 1번인 시험. 다 1번으로 찍으면 78점이다. 점수만 보면 손해가 없다.

### 그런데 대회 점수는 다르게 매긴다
- 정확도 기준: 전부 정상 → 약 78% (좋아 보임)
- macro F1 기준: 7클래스를 **똑같은 비중**으로 평균 → 정상만 F1 약 0.87, 나머지 6개는 0 → 0.87 ÷ 7 ≈ **0.125**

즉 **모델이 배우는 목표(합계 손실)와 대회 채점 기준(macro F1)이 서로 다르다.** 이 차이를 메우는 것이 class_weight다.

### class_weight="balanced"가 하는 일
클래스마다 **1행의 표 수**를 바꾼다. 공식: `전체 행 수 ÷ (클래스 수 × 그 클래스 행 수)`

| 클래스 | train 행 수 | 1행의 가중치 | 클래스 전체 비중 (행 수 × 가중치) |
|---|---|---|---|
| 정상 | 4,092 | 0.18 | 약 753 |
| 불량_Short_Shot | 469 | 1.61 | 약 753 |
| 불량_Blow_Hole | 233 | 3.23 | 약 753 |
| 불량_Exfoliation | 198 | 3.81 | 약 753 |
| 불량_Deformation | 106 | 7.11 | 약 753 |
| 불량_Stain | 100 | 7.53 | 약 753 |
| 기타불량 | 76 | 9.91 | 약 753 |

- 기타불량 1행을 틀리면 정상 1행을 틀릴 때보다 벌점이 약 **54배**(9.91 ÷ 0.18) 크다.
- 결과적으로 **7클래스가 전체 손실에서 똑같은 비중**을 갖는다. macro F1이 "7클래스를 똑같이 본다"는 것과 같은 생각이다.
- 대가: 모델이 불량을 적극적으로 찾다 보니 정상을 불량으로 잘못 부르는 경우가 늘어난다. 정상 점수는 조금 내려가지만 불량 6개 점수가 올라서 macro F1 전체는 오른다 (0.125 → 0.239).

## 28. "보폭"이 학습률(lr)인가?

맞다. 기본 경사하강법에서 가중치를 고치는 식은 다음과 같다.

```
새 가중치 = 지금 가중치 − lr × 기울기
```

- **lr(학습률)**: 모든 가중치가 **같이 쓰는 값** 하나
- **기울기**: 가중치마다 다르다. 그 피처의 값 크기에 비례한다

그래서 실제 이동 폭(lr × 기울기)은 큰 피처는 크게, 작은 피처는 작게 나온다. lr은 하나뿐이라 둘 다에 맞출 수 없다.
- lr을 작게 → 큰 피처는 안정적이지만 작은 피처는 거의 안 움직인다 → 반복이 길어진다
- lr을 크게 → 작은 피처는 잘 움직이지만 큰 피처는 튀어서 발산한다

표준화를 하면 기울기 크기가 비슷해져서 lr 하나로 모두 맞출 수 있다.

> sklearn `LogisticRegression`(기본 lbfgs)은 lr을 직접 정하지 않는다. 매 반복마다 보폭을 스스로 고른다. 하지만 보폭은 여전히 반복마다 하나라서 같은 문제가 남는다(표준화를 빼면 1,000회 안에 끝나지 않음). lr을 직접 정하는 것은 나중에 MLP(torch)를 만들 때다.
> Adam은 가중치마다 보폭을 따로 조절해서 이 문제를 줄인다.

## 29. "Stain recall 0.90"의 뜻

**실제 Stain 20개 중 18개를 모델이 Stain이라고 찾아냈다**(18 ÷ 20 = 0.90). 혼동행렬의 Stain **행**을 보면 된다.

하지만 precision은 0.159다. 혼동행렬의 Stain **열**을 위에서 아래로 더하면, 모델이 "Stain"이라고 답한 것은 113개다. 그중 진짜 Stain은 18개뿐이다(18 ÷ 113 = 0.159). 나머지 95개 중 66개는 정상이었다.
→ "Stain은 거의 다 잡지만, Stain이라고 부른 것의 대부분은 헛경보"

| | 혼동행렬에서 보는 곳 | 질문 |
|---|---|---|
| recall | 그 클래스의 **행** | 진짜를 몇 개 찾았나 |
| precision | 그 클래스의 **열** | 내 답이 몇 개 맞았나 |

## 30. class_weight는 켜고 끄는 것뿐인가? 강도를 조절할 수 있나?

**강도를 조절할 수 있다.** `"balanced"`는 미리 정해 둔 공식일 뿐이다. 클래스마다 가중치를 사전(dict)으로 직접 줄 수 있다.
```python
CLASS_WEIGHT = {"정상": 0.43, "불량_Short_Shot": 1.27, ..., "기타불량": 3.14}
```

쉬운 강도 조절 방법: balanced 가중치에 **지수(0~1)**를 씌운다. `가중치 = (balanced 가중치) ** 강도`
- 강도 0 → 모든 가중치 1 (= 끔)
- 강도 1 → balanced 그대로
- 강도 0.5 → 그 중간 (제곱근)

검증 실험 (로지스틱, 검증용 1,055행):
| 강도 | 정상 가중치 | 기타불량 가중치 | 정상이라고 답한 수 | 정상 recall | macro F1 |
|---|---|---|---|---|---|
| 0 (끔) | 1.00 | 1.00 | 1,054 | 0.999 | 0.125 |
| 0.25 | 0.66 | 1.77 | 993 | 0.960 | 0.240 |
| **0.5** | 0.43 | 3.14 | 782 | 0.806 | **0.306** |
| 0.75 | 0.28 | 5.57 | 467 | 0.501 | 0.303 |
| 1 (balanced) | 0.18 | 9.88 | 214 | 0.238 | 0.239 |

- 너무 약하면 전부 정상, 너무 세면 전부 불량. 중간이 가장 좋다
- 주의: 검증용 1번 나누기로 본 결과다. 소수 클래스가 15~20개뿐이라 운이 섞여 있다. 확정하기 전에 5조각 교차검증으로 다시 확인한다
- 이 강도는 **하이퍼파라미터**(사람이 정하는 설정값)다. 검증 점수를 보고 고른다

## 31. 이 모델은 선형인가? "직선 경계의 한계"는 무엇을 보고 아나?

### 선형인가: 예
로지스틱 회귀는 클래스마다 `점수 = 피처×가중치의 합`을 계산하고 가장 높은 점수의 클래스를 고른다. 두 클래스의 점수가 같아지는 곳이 경계가 되는데, 가중치 합이 같아지는 곳이라 **직선**이다(피처가 21개면 평면이지만 원리는 같다).
→ "압력이 높을수록 A 쪽"처럼 **한 방향**으로만 판단한다. "압력이 너무 낮거나 너무 높으면 불량, 중간이면 정상" 같은 판단은 직선 하나로는 못 한다.

### 한계라는 걸 아는 방법: 학습용 점수를 본다
혼동행렬만으로는 단정할 수 없다. 원래 구별이 어려운 데이터일 수도 있기 때문이다. 확실한 근거는 **모델이 이미 본 데이터(학습용)를 얼마나 맞히는지**다.

| 모델 | 학습용 F1 (본 문제) | 검증용 F1 (처음 보는 문제) |
|---|---|---|
| 로지스틱 | **0.242** | 0.239 |
| 랜덤포레스트 (비선형) | 0.590 | 0.302 |

- 로지스틱은 **답을 보고 공부한 문제조차 0.24밖에 못 맞힌다.** 공부를 덜 해서가 아니라 직선이라는 도구로는 더 잘 그릴 수 없는 것이다 → **과소적합(underfitting)**
- 랜덤포레스트는 같은 데이터에서 0.59까지 맞힌다. 직선이 아닌 경계라면 데이터에 더 배울 것이 있다는 증거다. 검증 점수도 0.302로 더 높다
- 반대로 학습용은 아주 높은데 검증용만 낮으면 → 외운 것 → **과적합(overfitting)**. RF도 0.59 vs 0.30이라 과적합 기미가 있다

> 진단 규칙: 학습용·검증용 둘 다 낮다 → 모델이 너무 단순하다. 학습용만 높다 → 외우고 있다.

## 32. balanced 가중치 숫자는 어디서 나오나? `** 강도`는 정확히 무엇을 하나? (10/21)

### balanced 공식
```
가중치 = 전체 샷 수 ÷ (클래스 개수 × 그 클래스 샷 수) = 5274 ÷ (7 × 그 클래스 샷 수)
```
| 클래스 | 샷 수 | balanced (강도 1) | 강도 0.6 | 강도 0.5 |
|---|---|---|---|---|
| 정상 | 4,092 | 0.184 | 0.362 | 0.429 |
| 불량_Short_Shot | 469 | 1.606 | 1.329 | 1.267 |
| 불량_Blow_Hole | 233 | 3.234 | 2.022 | 1.798 |
| 불량_Exfoliation | 198 | 3.805 | 2.230 | 1.951 |
| 불량_Deformation | 106 | 7.108 | 3.244 | 2.666 |
| 불량_Stain | 100 | 7.534 | 3.359 | 2.745 |
| 기타불량 | 76 | 9.914 | 3.960 | 3.149 |
| **기타불량 ÷ 정상** | | **54배** | **11배** | **7.3배** |

(train 전체 5,274행 기준. 30번 표는 검증 1번 나누기의 학습용 부분이라 숫자가 조금 다르다)

### 기준: 모든 클래스의 "목소리 총량"을 똑같이
- 샷 수 × 가중치 = 모든 클래스에서 약 **753** (= 5274 ÷ 7)
  - 정상 4,092 × 0.184 ≈ 753, 기타불량 76 × 9.914 ≈ 753
- 즉 4,092개짜리 정상과 76개짜리 기타불량이 학습에 같은 영향력을 갖는다 → 샷 1개끼리 비교하면 54배 차이 → 너무 세서 "애매하면 불량"을 배운다

### `** 강도`(거듭제곱)의 효과
- 1보다 큰 가중치는 줄고, 1보다 작은 가중치는 커진다 → 모두 1 쪽으로 당겨진다
- 클래스 간 배수도 같은 지수만큼 줄어든다: 54 ** 0.5 = √54 ≈ 7.3
- 순서(적을수록 무겁다)는 그대로, **얼마나 더 무거운지만** 줄어든다
- 0.5·0.6은 공식이 정해 주는 값이 아니다. 하이퍼파라미터라서 교차검증 macro F1로 고른다

## 33. class_weight는 로지스틱에서만 쓰나? RF·MLP에서도 쓰나? (10/21)

**생각(개념)은 모든 모델에 그대로 쓴다. 넣는 방법만 모델마다 다르다.**
- 생각: "적은 클래스를 틀리면 더 크게 혼낸다" → 불균형 데이터면 모델과 상관없이 필요
- 계산: `make_class_weight(y)`가 만든 `{클래스: 가중치}` 사전은 모델이 바뀌어도 그대로 쓴다

| 모델 | 가중치를 넣는 곳 | 가중치가 하는 일 |
|---|---|---|
| 로지스틱 | `LogisticRegression(class_weight=사전)` | 틀린 샷의 벌점(손실)에 가중치를 곱함 |
| RF | `RandomForestClassifier(class_weight=사전)` (같은 모양) | 나무가 가지를 나눌 때, 잎에서 투표할 때 적은 클래스 샷을 더 무겁게 셈 |
| MLP (torch) | `nn.CrossEntropyLoss(weight=텐서)` (`class_weight` 옵션이 없음) | 로지스틱과 같음 (벌점에 곱함). 사전을 LABELS 순서의 텐서로 바꿔 넣는다 |

### 주의
- **가장 좋은 강도는 모델마다 다르다.** 로지스틱에서 0.5였다고 RF도 0.5라는 보장이 없다 → 모델을 바꾸면 `main.py`의 `CLASS_WEIGHT_POWER`를 바꿔 다시 비교한다 (방식 B의 장점)
- 지금 `cross_validate`는 로지스틱 전용인 `n_iter_`(반복 횟수)를 출력한다 → RF에는 없어서 그대로 두면 에러. RF로 바꿀 때 이 줄을 같이 고쳐야 한다
- 가중치 말고 불균형을 다루는 다른 방법도 있다: 적은 클래스 샷을 여러 번 뽑기(오버샘플링), 예측할 때 기준선 옮기기(임계값 조정). 지금은 가중치 하나로 간다

## 34. 랜덤포레스트(RF)는 어떤 모델인가? (10/21)

### 나무 한 그루 = 스무고개
실제로 만든 깊이 2 나무 (train 5,274샷):
```
형체결력(Clamping_Force) ≤ 367 ?
 ├─ 예 → 공장 습도 ≤ 54.15 ?  → 잎 A / 잎 B
 └─ 아니오 → 용탕 온도 ≤ 661.1 ? → 잎 C / 잎 D
```
| 잎 | 정상 | Short_Shot | Blow_Hole | Exfoliation | Deformation | Stain | 기타불량 |
|---|---|---|---|---|---|---|---|
| A | 687 | 67 | 3 | 74 | 103 | 1 | 58 |
| B | 2,450 | 150 | 55 | 124 | 3 | 21 | 18 |
| C | 602 | 213 | 141 | 0 | 0 | 78 | 0 |
| D | 353 | 39 | 34 | 0 | 0 | 0 | 0 |

- 학습: 나눴을 때 양쪽이 가장 한 종류로 쏠리는 질문을 고른다 (첫 질문 하나로 기타불량 76개가 전부 왼쪽)
- 예측: 새 샷을 질문 따라 내려보내고, 도착한 잎에서 가장 많은 정답을 답한다
- 네 잎 모두 정상이 가장 많다 → 가중치 없으면 전부 "정상" → **RF에도 class_weight가 필요**
- 질문을 끝까지 하면 잎마다 1샷 → 학습용 100%, 처음 보는 샷엔 약함 (과적합) → `min_samples_leaf`(잎 최소 샷 수)로 브레이크

### 숲 = 서로 다른 나무 300그루의 다수결
- 랜덤 ①: 나무마다 샷을 무작위로 다시 뽑은 문제집 (같은 샷이 여러 번 가능, 평균 약 63%만 겹침)
- 랜덤 ②: 질문 고를 때마다 21개 열 중 약 4~5개만 보여 줌 → 모든 나무가 같은 질문만 하지 않게
- 나무마다 다른 곳에서 틀림 → 틀린 표는 흩어지고 맞는 표는 모인다

### 로지스틱과 비교
| | 로지스틱 | RF |
|---|---|---|
| 판단 | 점수 = 피처×가중치의 합 (직선) | 질문으로 구간 나누기 × 300그루 |
| 조건 조합 | 못 함 | "A 이하**이고** B 이하면" 가능 |
| 크기 맞추기 | 필요 | 불필요 (크다/작다만 봄) |
| 약점 | 과소적합 | 과적합 → 잎 최소로 조절 |

- 두 번째 질문에 **공장 습도**가 나옴 → "환경 열 = 시기 표지" 메모와 관련. 환경 열 빼고 재 보기 후보

## 35. 질문(열·기준값)은 모델이 정하나? 개발자는 하이퍼파라미터만 정하면 되나? (10/21)

**질문은 모델이 데이터를 보고 정한다. 개발자는 "어떻게 배울지"의 규칙과, 무엇을 보여 주고 어떻게 채점할지를 정한다.**

| 누가 | 정하는 것 | 이름 |
|---|---|---|
| 모델 (`fit`이 자동으로) | 어떤 열로 질문할지, 기준값(367 등), 잎마다 답 | **파라미터** (학습되는 값) |
| 개발자 | 나무 수, 잎 최소, class_weight 강도, 시드 | **하이퍼파라미터** (학습 전에 정하는 값) |
| 개발자 | 어떤 열을 넣을지, 결측 처리, 검증 방법(그룹 교차검증), 채점 기준(macro F1) | 데이터·실험 설계 |

- 기준값 고르는 법: 한 열의 값을 정렬해서 **이웃한 두 값의 중간**을 전부 후보로 시험한다 (그래서 367.00, 54.15 같은 값이 나옴)
- "가장 잘 가른다"의 기준: 나눈 뒤 각 쪽이 얼마나 섞여 있는지(지니 불순도)가 가장 많이 줄어드는 질문
- 로지스틱도 같다: 피처별 가중치는 모델이 학습(파라미터), `max_iter`·class_weight는 개발자(하이퍼파라미터)
- 개발자 몫이 더 크다: 모델은 **보여 준 열 안에서만** 질문할 수 있다. 쓸모 있는 열을 넣고 금지 열(shot_id 등)을 빼는 일, 점수를 믿을 수 있게 검증하는 일은 사람이 한다

## 36. HGB(HistGradientBoosting)는 무엇인가? 데이터 파트 추천안은 무슨 내용인가? (10/21)

### RF vs 부스팅
| | 랜덤포레스트 (RF) | 그레이디언트 부스팅 (HGB) |
|---|---|---|
| 나무 키우기 | 300그루를 동시에, 따로따로 | 한 그루씩 차례로 |
| 각 나무의 역할 | 각자 전체를 풀고 다수결 | 앞 나무들이 **틀린 부분을 고침** |
| 비유 | 학생 300명의 투표 | 한 학생의 오답 노트 100번 반복 |
| 예측 | 다수결 | 100그루의 답을 더함 |

- **Hist**: 값을 약 256개 구간(히스토그램)으로 묶어서 질문 후보를 줄임 → 빠름. 결측도 스스로 처리
- 부스팅은 오답을 계속 고치다 보면 **쌍둥이까지 외우기 쉽다** → 브레이크가 중요

### 설정 B
| 설정 | 값 | 뜻 | RF에서 비슷한 것 |
|---|---|---|---|
| `max_leaf_nodes` | 15 | 나무 하나의 잎 최대 개수 (작을수록 단순) | 잎 최소 |
| `learning_rate` | 0.05 | 오답을 한 번에 얼마나 고칠지 (작을수록 조심스럽게) | 없음 |
| `max_iter` | 100 | 나무 수 (반복 횟수) | 나무 수 |

### 데이터 파트 추천안 (`제출_추천_및_방법.md`, 7d31530)
- 전처리 `preprocess.load_data()` 그대로(피처 25개), 모델 HGB B + `class_weight="balanced"`, 환경 열 유지
- 팀원 측정 (시드 0·1 평균. 시드를 바꾸라는 뜻이 아니라 운에 덜 휘둘리려고 두 번 잰 것):

| 로지스틱 balanced | 0.224 | 0.228 |
| HGB A (기본) | 0.287 | 0.525 |
| **HGB B** | **0.308** | 0.402 |
| HGB B, 환경 열 제외 | 0.278 | 0.367 |

- A는 랜덤 분할만 높음 = 쌍둥이를 외움. B는 덜 외워서 그룹 분할이 더 높음
- test의 58%는 train에 쌍둥이가 있음 → public 점수는 랜덤 분할 쪽에 가까울 수 있음(A가 리더보드에서 더 높게 보일 수 있음). 그래도 구술에서 설명 가능한 B를 추천 (public 점수로 고르지 않는다는 원칙과 같음)
- 제출 팀당 10회, 먼저 0.2517을 넘는지 확인

### 우리 RF와 비교하려면
